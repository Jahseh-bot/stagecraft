# 测试质量详细工作指引

## 测前基线和计划

明确被测版本、目标环境、构建来源、已评审AC/设计/接口、已有测试/缺陷、可用账号与数据、审计或修复授权。只有URL时明确源码层无法验证；只有源码时不能声称真实托管服务通过。

先使用内置 test-case-design 完成用例设计、补漏和评审，保存AC→TP→TC→执行方法映射。测试方案比较覆盖与成本，推荐项在前，用户可自由补充；用例产物展示并获评审通过后才执行。

## 按风险选择验证层级

| 层级/方向 | 何时适用 | 需要保存的证据 |
| --- | --- | --- |
| 静态/构建 | 代码、配置或依赖变化 | 实际工具/版本/命令、输出与退出状态 |
| 单元/规则 | 纯逻辑、分区边界、状态规则 | 具体测试名、数据、断言与TC映射 |
| 集成/契约 | 模块、数据库、外部API或事件交互 | 测试依赖与真实/模拟边界、契约结果 |
| 端到端 | 核心用户流程、关键错误恢复 | 版本、账号角色、操作、截图/日志及状态变化 |
| 数据/迁移 | 数据模式、导入导出、历史数据和重跑 | 前后校验、样本来源、失败/恢复证据 |
| 多端/可访问 | 实际支持的屏幕、浏览器、设备、键盘与语义 | 代表环境与人工/自动检查边界 |
| 性能/容量 | 已约定目标或性能相关改动 | 负载模型、基线、目标来源、测量环境和结果 |
| 权限/安全 | 资源访问、身份、外部输入和敏感操作 | 允许范围内的正反向权限/输入检查；专项审计缺口 |
| 可靠性/恢复 | 重试、并发、队列、离线或依赖失败 | 可控故障、恢复后状态、重复副作用检查 |
| AI评估 | 概率输出、工具调用、检索或生成结果 | 版本化样本、判定标准、重复性/误差与成本观察 |

层级不是每次全部执行。按变更、风险和用户确认范围选择；高风险缺口不能只因运行慢而消失。压力、安全攻击、真实付费和破坏性故障注入必须在适用授权与隔离环境内，不能用生产数据随便试。

## 环境与数据准备

使用可重复的初始化与清理流程；避免测试相互依赖或污染真实数据。说明账号权限、种子数据、时间/时区、网络条件、外部服务替代与能力限制。稳定定位和可观察等待优于固定长延时；模拟只能证明模拟边界内的行为。

现有测试先建立基线，区分历史失败。测试计划中记录不执行的检查及原因、影响和用户风险决定，不能把not_run或blocked算通过。

## 执行、诊断和回归

按已评审用例逐条记录结果，先核心风险再约定回归。失败保存环境、最短复现、预期/实际、日志与缺陷ID；偶发失败记录发生条件，不反复重跑直到绿灯。

缺陷分清产品问题、测试错误、环境问题和未定需求；修改业务规则先讨论，不能把实现现状改成预期。修复范围内用证据定位，回归原失败用例和影响范围。修复改变build成果时，更新其验证和评审基线，再继续受影响测试。

## 测后评审与发布建议

展示用例集版本、执行覆盖、缺陷严重性、修复/回归和剩余风险。区分需求覆盖、用例通过率和代码覆盖率，给出各自分母；任何单一百分比都不代表质量全面。

建议可以是可进入发布评审、需修复后重测或当前无法判定，必须说明依据。测试阶段的评审不自动授予部署权限。交给deploy的应是明确被测版本、环境差异、必须上线后复核的路径及已知限制。
