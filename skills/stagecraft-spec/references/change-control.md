# 全链路变更联动

## 原则：按关联传播，不按所在阶段截断

任何阶段、任何产物都可以发起变更：创意、PRD、设计源稿、交互文案、架构、代码、测试用例/结果、README、官网教程、发布清单和外部设计文档。当前处在测试阶段，不意味着不能回到需求；用户改了PRD，也不能只改文档而留下旧设计、旧代码和旧用例。

“联动”是agent完成影响分析、同步修改、验证、展示并等待评审的工作闭环，不是把一份文本无差别覆盖到所有文件。所有涉及同一规则的产物必须一致；无关内容保留。不确定是否受影响必须记录待核实，不能默认为无影响。

既有用户明确要求的改动就是修改授权，直接落实其明确范围；新产生的产品取舍、范围/费用/架构变化先给推荐与选项。不能借联动绕过每阶段展示后结束本轮、用例评审后执行、发布前确认等门禁。“全部同步”不预先批准还没展示的修订成果，也不授权自动重新发布。

## 维护双向关联

在项目中保存可读的关联表（例如docs/traceability.md）和机器可读图（例如docs/traceability.json）。已有编号沿用，不为了工具重编号。

节点包含稳定ID、所属阶段、真实项目相对路径、可选章节/外部对象定位和描述；关系包含两个节点和关联理由。关系可表示定义、实现、验证、说明、发布或引用。方向用于解释语义，影响分析沿两个方向遍历；同一文件中的节点也要共同核查，避免只改一处留下同文件矛盾。

覆盖示例：AC-05每日容量 ↔ DS-04满额提示 ↔ ADR-02容量约束 ↔ CODE-03新增事务 ↔ TC-08第四项拒绝 ↔ DOC-02使用说明。测试发现规则不合理，沿同一关系反查PRD/设计；如果实现违反已有规则，只修实现和回归，不擅自改变需求迎合代码。

每次交付后更新关联图，文件改名/删除保留旧ID、替代ID和原因。不能只关联代码，遗漏原型、错误文案、数据样例、截图、部署配置与教程。未产生的下游产物记录“待生成，使用新基线”，不伪造完成产物。
外部文档记录URL/对象ID/版本与本地清单；没有写权限或验证能力时记录blocked，不能用本地说明冒充外部已更新。

## 变更闭环

1. **记录CR**：保存用户原话/真实来源、发现位置、原规则→新规则、原因、当前阶段和已批准版本。可用docs/changes/CR-xxx.md；旧提交快照、反馈、测试结果不可覆盖。
2. **双向分析**：从改动的AC/产物出发，遍历需求、设计、技术、实现、用例、说明、发布记录；查找引用和重复描述。图不完整或找不到起点，保守检查整个工作流，并补齐缺口。展示影响清单，不让用户手工找文件。
3. **分类处置**：每项记录“需修改 / 保留但须复核 / 待生成 / 不受影响（理由）/ 外部阻塞”。注明具体路径、旧版本、预期新版本、负责人agent、验证方法和评审状态。不能只写“下游待更新”。
4. **使旧依据失效**：相关产物的旧批准/旧测试不能代表新版本。暂停依赖旧依据的执行；保留无关事实和已有选择。辅助状态机为保守线性阶段门禁，可能要求后续阶段重新检查，但不要求重写无关文件。
5. **同步真实产物**：从最早受影响的基线开始，按依赖顺序修订；同时检查反向规则一致性。设计须改实际源稿/预览，代码须改实际逻辑，用例须改数据/步骤/预期，文档须改具体说明。新用例未经评审不执行；已经运行的旧结果保留并标记不适用。
6. **逐阶段展示**：完成当前修订后展示差异、自检、影响矩阵与剩余项，结束当前轮等用户评审。收到真实批准后，自动携带CR进入下一受影响环节，不重复问已确认的同一个变更。下游还有独立关键选择才另行讨论。
7. **验证闭环**：复测原失败及相关回归，对照PRD—设计—代码—测试—教程的一致性；保存新版本/TC/运行证据。图、工作流与报告一致后方可关闭CR。有blocked/not_run或未确认产物时保持开放，不报“全链路已同步”。

### 变更矩阵模板

|CR|关联ID / 路径 / 阶段|原→新内容|处置及理由|版本 / 提交|验证证据|用户评审|状态|
|---|---|---|---|---|---|---|---|

每次回复简述已同步、待评审、未同步和具体阻塞。旧线上版本、npm发布和外部设计源的真实状态必须分别说明；更新仓库文件不等于已更新线上。

## 交接助手（agent操作，用户不用输命令）

注册真实产物关联图：

```json
{"nodes":[{"id":"AC-05","stage":"spec","path":"PRD.md","label":"每日最多三件"},{"id":"TC-08","stage":"test","path":"qa/cases.md","label":"容量边界用例"}],"edges":[{"from":"AC-05","to":"TC-08","reason":"用例验证容量要求"}]}
```

```sh
node /path/to/skill/scripts/handoff.mjs trace --workflow /absolute/workflow --record /absolute/traceability.json
node /path/to/skill/scripts/handoff.mjs change --workflow /absolute/workflow --record /absolute/change-input.json
```

change-input示例（不构成真实用户要求）：

```json
{"originStage":"test","roots":["TC-08"],"summary":"用户要求调整每日容量，联动修改全部引用","source":"实际用户消息标识或原话来源"}
```

助手保存图/CR快照、双向遍历节点，发现改动文件时也反向使相关基线失效；同文件节点联合核查。没有图、覆盖不全或未知根节点时保守失效全链路。节点来自当前授权阶段范围，不借此新增项目目标。工具不能推理文件语义、保证图已穷尽依赖或自动修改任意外部系统：agent仍须搜索引用、核查实际内容和执行同步。

已开始的受影响阶段必须产生新的验证与真实用户批准；未开始阶段仍pending，后续使用更新后的基线。保持图稳定至开放CR处理完成，不能通过删除边/节点来缩小已经登记的责任范围；新发现影响开补充CR，不伪装旧分析完整。新增/改名产物在阶段提交中登记，关闭CR后更新图，未覆盖新文件时助手自动退回保守检查。

关闭CR需要每个受影响节点的处置：updated / retained / removed、理由、属于当前已批准提交的证据路径；保留/更新文件必须在该阶段提交中，删除文件必须实际不存在且有已批准的删除说明。每个受影响已开始阶段都必须是新的completed提交，不能用旧批准关闭。

```json
{"change":"助手返回的CR UUID","summary":"相关修订均已验证和评审","items":[{"id":"AC-05","action":"updated","reason":"落实新规则","evidence":"docs/spec-checks-v2.md"},{"id":"TC-08","action":"updated","reason":"更新边界与预期并执行","evidence":"qa/results-v2.md"}]}
```

```sh
node /path/to/skill/scripts/handoff.mjs change-close --workflow /absolute/workflow --record /absolute/resolution.json
```

启用关联图/CR的工作流使用v3，旧助手会拒绝处理，防止忽略变更责任。普通v1/v2可由新助手读取；注册关联时升级，原提交历史保留。没有Node时维护等价Markdown矩阵和版本记录，不宣称工具校验已执行。工具只校验记录、文件、版本和门禁，真实评审及语义完整性由agent忠实执行。
