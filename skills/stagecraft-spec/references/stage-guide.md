# 需求与PRD详细工作指引

## 入口与基线

读取已确认产品方向、现有PRD/工单、真实行为及设计约束。缺少上游报告可直接工作，但不能把自己推断的功能当成用户选择。区分现状、目标、迁移过渡状态和非目标。

PRD按项目规模组织：背景/问题、目标与成功判断、角色/场景、范围与优先级、流程、功能与规则、数据/权限、非功能约束、依赖/风险、验收矩阵、待决问题、版本/评审记录。已有格式优先，不为空目录造文档。

## 需求逐项展开

| 对象 | 必须回答的适用问题 | 输出形式 |
| --- | --- | --- |
| 角色 | 谁能看/创建/改/删什么，所有权或租户边界是什么 | 角色—资源—操作矩阵 |
| 功能模块 | 用户触发什么动作，输入/输出是什么，是否本期做 | 功能清单、优先级与非目标 |
| 核心流程 | 正常、替代、异常、取消、重试、恢复如何走 | 流程图或编号场景 |
| 状态与规则 | 什么条件允许什么转换，冲突与重复操作怎样处理 | 状态表、条件/动作决策表 |
| 数据 | 字段类型/必填/默认/边界，精度、唯一性、时区、保留与删除 | 数据字典和生命周期说明 |
| 外部交互 | 超时/失败/限流/部分成功，用户怎样获知和补救 | 契约需求与错误场景 |
| 质量约束 | 用户需要何种响应、可用性、兼容与可访问性 | 有依据的目标、测试方式与边界 |
| 业务度量 | 如何判断价值实现，事件和数据是否必要 | 指标定义、采集边界与依据 |

权限、金额、退款、数据删除、AI输出责任等规则有歧义时先讨论，不靠通用模板补全业务事实。只有当产品具有相关能力时展开该维度。

## 验收标准

每条范围内需求赋稳定 AC ID，写清前置状态、动作/输入、可观察输出及状态变化。验收说明正常路径、适用的边界/非法输入/恢复行为和验证方式。大需求拆成独立可观察结果，避免“系统功能正常”“满足高并发”这类无法判定的语言。

示例结构：`AC-7 / 来源 / 角色与前置条件 / 输入或动作 / 输出及副作用 / 异常处理 / 验证方式 / 依赖与待决问题`。具体数字、文案和性能目标来自需求或讨论，未确定就标待定并说明影响。

检查覆盖：每项范围映射AC；每个AC可测试；同一状态没有矛盾规则；需求与非目标不冲突；数据定义与界面/接口一致。架构细节可留给后续，但影响产品行为的决定不能后移成开发默认。

## 讨论、评审与变更

按依赖次序讨论范围 → 流程/角色 → 规则 → 验收，选项1为推荐方案并说明理由，允许自定义补充。用户可一次确认一组关联规则，不逐字段机械提问。

完成PRD后保存并展示完整文档和核心流程，标明相对上版差异及未知项，等待用户评审具体版本。有影响验收的未决规则时只交付草案，不放行依赖的设计和实现。

修订保留AC ID；废弃项标注替代关系，不重新编号掩盖历史。记录变更对页面、接口、数据、测试和发布的影响，传给下游重新评审。
