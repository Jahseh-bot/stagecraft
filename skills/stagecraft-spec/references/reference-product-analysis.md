# 参考产品研究与 REA

本指引是 Stagecraft 自研适配层。REA 官方来源：https://github.com/morluto/rea 。能力依据2026-10-30查阅的官方README与随包捆绑的 reverse-engineer-anything 指引；实际可用能力以宿主暴露的工具和当前安装版本为准，不把工具名列表当作已执行证据。

## 触发与范围

需求、用户消息或现有PRD引用具体参考产品、对标功能、网址、安装包或运行实例时触发。仅提到Vue等技术选型不触发产品逆向；只有截图时先分析可见交互，不声称已知道内部实现。

从上下文提取对象及功能范围。仅有“参考某某”且可能指多个产品/多个版本时，先定位官方入口或项目中明确提供的材料；无法唯一确定再询问。不要自行选用附近安装包、测试夹具或其他项目的目标。

在既有阶段方案中讨论研究深度，不重复询问已明确的范围：
1. 推荐：围绕拟采纳的核心功能追踪用户操作、状态、数据和关键技术，足以支撑当前PRD，控制研究成本。
2. 扩展：增加相关子系统、边界和版本差异分析，适合这些机制会影响产品决策的情况，成本更高。
最后允许自由文字补充。用户已明确要求分析的范围直接复用。禁止把“参考一个功能”扩成整个产品复制。

## 按目标分流

|现有材料|研究方式|结果边界|
|---|---|---|
|完整源码仓库|普通源码/代码图工具追调用、状态和数据契约|不为源码阅读强制启动REA或配置检查|
|ASAR、提取的JS/Electron应用|REA analyze_javascript_application，先摘要再按功能追踪|静态可达路径不等于实际执行|
|网页或已打开的应用运行实例|用可用的REA浏览器/Electron目标发现与场景捕获，按所选操作观察|页面和客户端流量不能证明不可见的服务端内部实现|
|原生、托管、移动应用包|根据REA当前工具说明选择包清单、托管分析或原生分析路径|依赖对应平台/分析引擎，未恢复部分明确unknown|
|截图、公开说明、无可访问目标|可见流程分析/文档研究，记录尚缺材料|标记partial，不声称做了代码级逆向|

优先使用已连接REA的实际工具schema。操作前读取 [内置REA技能](upstream/reverse-engineer-anything/SKILL.md) 及对应目标引用；技能原文随包完整保留，Stagecraft的研究范围和阶段评审规则优先。不能只写“已调用REA”。安装Stagecraft或REA skill不等于注册MCP或安装分析引擎。

缺工具/提供方时记录具体缺口。可用CLI且范围允许时按官方文档使用对应分析命令，记录实际版本和完整输出位置；不要从本指引猜参数或固定追随latest。若需修改MCP配置、替换本机技能或安装引擎，先给实际变更计划，再按宿主要求取得授权。没有必要能力时先完成可见行为/源码/公开文档研究；影响核心需求的未知项须保留待决或blocked，不冒充闭环。

## 追踪核心技术与逻辑

按功能问题清单分析，而非无限扫描整包。每项至少追踪：入口/触发 → 输入与校验 → 状态转换 → 关键模块或调用 → 数据读写/网络契约 → 输出 → 失败/重试/冲突路径。

总结适用的核心点：模块职责、状态机、数据模型与生命周期、关键算法或调度、接口边界、缓存/持久化、并发/离线/恢复、限制与技术依赖。不适用写原因，不凭空补齐不可见模块；性能和安全特性没有证据就不作确定结论。

先读摘要和证据，再针对缺口查询。大结果被截断时用工具支持的分页/证据视图/导出，不把截断输出当完整结果。记录来源位置（函数、模块、请求、页面动作、截图等）、Evidence ID、版本或文件摘要和覆盖范围；动态行为需要运行观察支持，不能仅凭字符串判断。

只在用户指定目标和操作范围内研究。使用现有合法访问权限，不绕过登录、付费或访问限制；提交、支付、发送、删除等外部副作用不能因“研究参考产品”自动获得授权。保存证据时去掉凭据、Cookie和用户私密内容；结论可复用不等于可以直接复制受限制的代码或素材。

## 必须保存到 spec 的成果

沿用项目已有规格目录；没有时使用 docs/spec/references/<product-id>/，不另造互相冲突的PRD。至少保存：

- analysis.md：目标身份/版本、范围、实际使用的工具及版本、核心功能和技术链路、业务状态与失败路径、证据索引、限制与待决问题。
- evidence/：可留存的脱敏输出、场景记录、截图或导出；工具Evidence ID可能随会话失效，不能只留下临时ID。无法导出时保存关键观察、来源定位、命令和重现步骤，并注明缺口。
- 在PRD增加“参考产品分析与采纳”章节，直接写核心摘要及完整报告链接，不能只丢一个外链。

建议结论表：

|REF-ID|参考功能/核心逻辑或技术|事实 / 推断 / 未知|来源、版本、Evidence ID或本地证据|采纳 / 调整 / 不采纳 / 待确认及理由|本项目AC / 架构待决项|
|---|---|---|---|---|---|

业务行为转成可观察AC；参考产品的内部技术写为证据和候选方案，不直接绑定本项目架构。未确认采纳的内容不能写成已批准需求。范围与深度决定已确认，也不能代替对研究结论和PRD的评审。

示例：观察到输入停止后才出现结果，只能确认可见时序；若没有实现或可靠运行证据，“使用防抖、具体延时、服务端排序算法”仍是推断/未知。本项目可以另行讨论响应方式和验收阈值。

## 交接与变更

报告按问题清单标 answered / partial / unresolved。展示核心逻辑、采纳建议、证据和未知项，推荐项放第一，允许自定义意见；结束本轮等用户评审。依赖核心未知项的PRD不能当作完整基线，不直接进入开发。

把研究报告、关键证据与PRD一同列入spec阶段receipt，加入 REF-ID ↔ AC ↔ 设计/架构 ↔ 代码/TC 的关联。参考版本、发现或采纳决定变化时按 [全链路变更协议](change-control.md) 建立CR，复核下游，保留旧证据；不能静默把参考行为当成始终不变的事实。
