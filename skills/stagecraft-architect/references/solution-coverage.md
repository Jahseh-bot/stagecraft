# 完整技术方案与选型覆盖

## 目的与触发

在架构阶段提出技术方案前读取。完整意味着覆盖产品实际需要的能力、运行链路和生命周期，不是罗列全部框架或要求所有项目安装缓存、消息队列、Kubernetes。局部修改可聚焦受影响范围，但必须说明复用的系统边界和未改变的已有技术。

“React + TS”“Vue + Vite”只回答部分客户端实现。用户选择过前端框架，不代表批准了后端、数据平台或托管商。全栈项目必须交代业务在哪里执行、数据在哪里持久保存、权限在哪里强制检查、如何部署与恢复；BaaS/全栈框架也必须展开这些职责，不能用一个产品名代替说明。

## 1. 先建立约束，不从技术偏好出发

从已批准PRD、设计、参考产品研究与现有代码整理：

- 使用端与入口：Web、移动/桌面、CLI/API；SEO/首屏/离线/实时要求；公开页与登录区。
- 业务性质：核心流程、事务边界、角色/租户、文件或媒体、搜索、异步任务、外部服务；AI、支付只在产品确有需求时分析。
- 数据与质量：敏感程度、保留/删除、查询方式、已知数据量/并发与增长假设、可用性、可接受的数据损失和恢复时间。
- 交付约束：现有技术、团队能力、上线目标/地区、预算、供应商限制、自托管要求、已有账号和运行环境。

已确认事实、暂定假设与待用户选择分开。容量/预算未知就给出带条件的方案和验证计划，不捏造流量或费用。只集中询问会改变核心方案的缺口；复用已选项，不让小白自行拼一串技术名。

## 2. 技术能力覆盖表（先于候选方案）

每行标记“采用 / 复用 / 不适用 / 待决”，给出AC或约束依据、承担职责的组件、边界与验证方式。以下是必须检查的维度，不是必须安装的技术。

|能力层|需要落到具体方案的问题|
|---|---|
|客户端与渲染|端类型、语言/框架、SPA/SSR/静态生成选择、路由、表单/校验、服务端数据同步与客户端状态边界|
|界面工程|组件/样式体系、设计稿实现、可访问性、国际化（适用时）、静态资源与浏览器支持|
|业务执行/后端|语言、运行时、框架、模块组织；单体/分服务/托管函数选择；业务规则与事务由哪个可信执行端负责|
|API与契约|HTTP/RPC/事件或其他接口的理由、schema、错误、分页、版本兼容、输入验证、幂等和超时|
|身份与权限|登录/会话或令牌、服务端授权、角色/租户隔离、撤销/退出、管理入口；无登录也要说明数据访问边界|
|主数据存储|数据库类型与具体方案、实体/关系、约束、索引依据、事务、连接管理、查询/ORM选择、迁移与旧数据兼容|
|文件/媒体|对象存储或其他保存方式、上传校验、访问授权、生命周期、媒体处理；无文件则说明不适用|
|缓存/会话/限流|是否需要独立缓存、键与过期、失效和一致性；不能因“全栈”默认加Redis|
|搜索/检索|数据库查询是否足够，何时需要独立全文/向量索引、索引同步、排序与权限过滤|
|异步/定时任务|执行进程、任务保存、队列是否必要、重试上限、去重、死信/补偿、部署时的任务处理|
|实时协作/推送|轮询/SSE/WebSocket或其他机制、连接规模假设、鉴权、断线恢复与顺序；无需求则不增加|
|外部集成|邮件/消息/支付/第三方API的适用性、webhook验签、幂等、限流、超时、失败和对账责任|
|AI能力（有需求时）|模型/提供方、调用后端、流式输出、工具边界、评估集、成本额度、失败回退；RAG/向量库按实际需求选择|
|安全与隐私|信任边界、服务端校验、敏感配置、凭据轮换、输入/输出、依赖风险、日志脱敏、数据删除|
|工程组织|仓库/模块或包边界、语言与版本锁、依赖管理、环境配置、代码规范、契约/类型共享方式|
|测试与质量|单元/组件/接口/数据库集成/E2E的适用分工、隔离数据、迁移/权限/并发回归、性能或安全专项依据|
|运行与部署|客户端/API/数据库/worker分别运行在哪里、构建产物、运行时兼容、域名/TLS/路由、网络边界、环境隔离|
|CI/CD与发布|构建/检查/迁移顺序、凭据来源、预览/测试/生产、发布与回滚条件、数据变更不可逆时的恢复方式|
|可观察与运维|结构化日志、错误/指标/追踪适用性、健康检查、告警对象与处理、备份、恢复演练和维护责任|
|容量/成本/演进|负载依据、瓶颈、资源与服务费用项、配额、托管绑定、退出路径；扩容或拆服务的可观察触发条件|

单机工具可以全部由浏览器/本地进程承担，但必须说明为什么不需要服务端以及跨设备、权限、备份等边界。不能为了覆盖表把新功能强加给PRD。

## 3. 给2–3套完整而有差异的候选方案

每套方案填写同一张表，至少覆盖所有“采用/复用”的层；不适用沿用覆盖表理由。每个适用层写具体技术/服务、职责、与其他层的连接方式；未知版本/服务能力显式标待验证，不能用“配一个后端”占位。逐项讲清选择后用户会获得什么、要维护什么。

|技术层/决策|方案1（推荐）|方案2|方案3（确有价值时）|
|---|---|---|---|
|前端与渲染|技术、职责与运行方式|同维度|同维度|
|后端与API|语言/运行时/框架、业务模块和契约|同维度|同维度|
|数据/身份/文件|具体方案、权限边界与持久化责任|同维度|同维度|
|条件能力|任务、缓存、搜索、实时、集成等采用或不采用及理由|同维度|同维度|
|工程与测试|开发工具、测试边界与CI方式|同维度|同维度|
|运行与运维|每个进程/服务的部署位置、备份恢复、可观察性|同维度|同维度|
|整体取舍|满足哪些AC；开发/维护/费用/约束；为什么推荐|优势、代价、适用条件|优势、代价、适用条件|

候选可以围绕“托管一体化”“前后端分离的模块化单体”“复用现有后端/企业平台”等不同运行和责任结构组织，但这只是组织方式示例，不是通用推荐排序。选择必须由当前约束决定；不要做三套仅替换React/Vue的伪架构对比，也不要为了凑第三项推荐明显不适合的微服务。

组合交叉检查：语言/运行时版本与依赖兼容；宿主是否支持长连接和后台任务；数据库事务/连接/迁移是否匹配；身份凭据如何传到API并做授权；文件权限与数据权限是否一致；本地和生产环境是否能复现。需要最新能力、版本、支持状态和价格时查官方资料并记录日期；估算注明负载假设，不编造精确费用。

推荐理由必须能追到AC、团队约束或实际探针，例如“既有后端可复用，减少一次数据迁移”，而非仅“热门、成熟、可扩展”。列出推荐方案不适合的条件。逐层保留用户已选技术，提供可自定义/组合选项；用户组合跨方案组件时重新检查契约、运行环境和职责缺口，不能直接拼接当作已验证。

## 4. 整体选择后再深入，成果仍须评审

方案讨论时展示技术覆盖、候选组合和关键未知项并停下。用户确认整体方案后，在确认范围内完成详细设计与必要隔离探针；遇到新的关键取舍再讨论，不逐个函数询问。

最终架构报告至少提供：

1. 系统边界/部署图：客户端、业务执行、数据及外部服务，标注信任边界、运行位置和通信方式。
2. 一条核心业务链路的端到端时序：界面→鉴权→API→业务规则→事务/外部动作→响应及失败补偿；对适用的异步路径另说明。
3. 数据模型与接口契约实例，包括权限、错误、并发/幂等和迁移；参考产品逆向结论以REF-ID引用，不能把推断当事实。
4. 技术选型清单：组件、用途、版本/兼容范围、选择依据、官方来源和核查日期、验证状态、维护与替换条件。
5. 环境与交付计划：启动组件、配置名（不含密钥）、测试隔离、构建/部署/迁移/回滚、日志告警与备份恢复。
6. AC→模块/接口/数据→实现任务→测试映射；候选被排除原因、风险、未决项与证据。

## 5. 完整性门槛

交付前逐项自检并保存结果：

- 每个适用能力都有明确承载者；无适用层被只写前端框架、空白或“以后补”遮盖。
- 不同候选比较的是同一范围；全栈主链路至少能在纸面从入口走到数据持久化并返回。
- 权限校验和秘密不依赖不可信客户端；业务事务、第三方失败和数据恢复有明确责任。
- 开发计划的每项工具/服务均能追到所选方案；未选技术不得偷偷出现在实现计划中。
- 没有把未运行探针记为passed；关键选择或可行性仍未知时标pending/blocked，不能宣布完整可实施。
- 每阶段产物仍展示后结束本轮等评审。后续架构变化按 [全链路变更协议](change-control.md) 影响PRD、设计、代码、测试和部署资料；不因“全面补齐”跳过用户决定。

这里是agent执行和交付的完整性要求，不宣称交接助手能够自动判断技术方案的语义质量。
