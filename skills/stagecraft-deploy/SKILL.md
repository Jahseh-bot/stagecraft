# 部署与发布验证

在当前 coding agent 中直接完成本阶段，不启动嵌套模型或要求用户操作 runner。先阅读本技能内的 [统一执行与交接协议](references/protocol.md)，它定义自主决策、有限修复、授权边界与跨阶段恢复。用户目标与项目约定优先；不要求安装其他阶段技能。

## 强制阶段停顿：展示后结束本轮

一个阶段的闭环不等于一次对话跑完整个项目。方案待选择时结束当前轮等待回复；本阶段成果保存、自检并展示后，必须提交为 awaiting_review，用最终回复结束当前轮，停止工具调用，不加载或执行下一阶段。不能在同一轮自己写 review、complete 或假定用户通过。

最终回复只交付当前阶段：阶段名称、提交版本、可打开的产物/预览、变化与验证结果、待评审要点；给出推荐处理方式及理由、其他可行选项，并允许自由文字修改。下一阶段只注明名称，不提前产出下一阶段方案或成果。

只有展示该版本之后收到的真实用户回复，才可作为该版本的评审。收到修改意见时留在当前阶段，修订、自检、重新展示新版本并再次结束本轮；“改完继续”不代表批准尚未展示的修订版。明确通过后才记录 review/complete，并在新一轮进入下一阶段的方案讨论，等选择后执行。方案确认不是成果确认；回答澄清问题不是阶段验收；“全自动做完”不能预先批准未来成果。

只有创意时从 discover 开始，有 PRD 草稿时从 spec 开始；不得因回答了几个问题就跳到 build。复用已有上游成果必须记录真实路径、有效版本和明确评审依据；缺少必要的产品、需求、设计或架构基线时回到对应阶段逐个交付评审，不能藏在开发阶段内一次补齐并直接编码。单阶段修复或测试请求仍按真实范围执行，不强制重走无关阶段。

## 接手与恢复

识别用户的目标、当前项目、入口与终点。已有匹配工作流时读取交接记录、真实成果和验证证据，复用已确认决定；输入改变则重新检查相关结论。没有上游成果时补足本阶段必需输入即可开始，不为凑齐七阶段而要求重复采访。

## 每个阶段与环节的方案讨论

部署平台、本地或公网、访问范围、资源费用及重大数据迁移策略。给出适合项目的目标方案、限制、成本和推荐理由，确认后发布；已有明确且仍适用的目标和授权不重复询问。不得因另一个平台更方便而自行切换。

每个阶段开始时先讨论本阶段方案；每个涉及选择的环节执行前，列出 2–3 个实际可行的选项，第一个始终是 agent 最推荐的方案，并解释推荐理由、适用条件与取舍。最后始终提示“如果都不合适，可以直接输入你的想法、约束或组合方案”。等待用户实际回复后再执行依赖该选择的工作；默认选中、沉默和等待超时都不算确认。已有明确选择直接复用，说明依据；用户明确委托的范围按委托执行。

遵循统一协议的决策门槛：先给具体方案和推荐理由，等待用户选择确认；记录决定及来源。用户已明确选择或明确委托的范围直接复用，不重复确认。待确认时只推进无依赖的调研或方案预览，不实施依赖该选择的成果。

## 覆盖范围与详细操作

开始工作时读取 [跨阶段覆盖与裁剪](references/coverage.md)，建立本任务适用性矩阵，再读取 [本阶段详细工作指引](references/stage-guide.md) 中对应环节。逐项记录适用、不适用或未知的依据，把适用检查连接到具体产物、验证和评审；不能把清单勾选当成已验证。项目越小材料越精简，但不省略有实际风险的环节。

宿主工具不同或三方引用缺失时，读取 [三方只读适配说明](references/upstream-adapters.md)。第三方方法只读：不修改或删除其原始文件、示例与许可证。宿主适配和覆盖补充写在自研层，按当前任务读取匹配方法；缺少专项能力明确说明，不假装通用流程已经完成专项审查。

## 执行闭环

1. 确认用户指定的目标、环境、版本/构建产物、权限和发布范围。读取测试证据与项目配置；没有前序报告时自行完成必要发布前检查。目标、访问范围或费用方案尚未确认时先提供选项让用户选择；发布权限缺失时说明具体阻塞，不能把本机目标擅自改成公网。
2. 使用现有托管平台、CI/CD、容器、静态托管或进程管理方案；按实际项目选型，不强制 Docker。查验平台当前官方配置。复用既有凭据机制，密钥不写入报告、源码或聊天。
3. 生成必要部署配置、健康检查、环境变量名称说明和回滚步骤。在授权环境先验证构建、配置和关键前置条件；数据迁移、付费资源或不可逆操作只在所需授权明确时执行。
4. 实际发布前，将具体发布清单（目标、版本、测试结论、配置/迁移影响、回滚步骤）保存并展示给用户评审；确认该版本后才执行实际发布，记录目标、修订版本、时间和可观察部署结果。构建成功、推送成功或进程启动不是发布成功；等待平台报告结果，并检查实际目标地址与关键用户路径。
5. 发布失败先诊断日志，做范围内可逆修复后重试。存在旧实例时核对正在运行的版本，不能以旧服务健康冒充本次上线。检查失败且继续会扩大影响时按已授权回滚计划回滚，验证回滚结果并如实报告本次失败。
6. 在外部凭据、账单、DNS或平台故障阻塞时保存具体状态、已完成动作和恢复路径，不重复执行可能已成功的发布。成功时交付实际访问地址、版本证据、健康结果、回滚与后续更新方法。

## 产物展示与用户评审

遵循 [产物、评审与变更规范](references/artifact-reviews.md)，将本阶段实际成果存入项目并更新产物目录；主动展示可打开的文档、可见设计预览、运行演示或验证结果。提交具体版本供用户评审，记录反馈，按意见修改、自检并重新展示差异。方案确认不能替代成果评审；当前版本未经用户明确通过，不标 completed、不执行依赖它的下游工作。任何时候收到修改意见，都保留旧快照与评审记录，分析并重新验证受影响下游。

## 本阶段交付与验收

交付：可重用部署配置、发布记录、实际地址与修订版本、健康/关键路径证据、回滚和更新说明。

完成条件：目标与授权一致；实际发布版本已确认；目标健康与关键路径已验证；没有仅凭构建/推送宣称上线；失败或回滚结果准确记录。

使用 [报告模板](assets/report.md) 保存目标、AC、成果、实际证据及剩余问题。用 [交接助手](scripts/handoff.mjs) 记录阶段；无 Node 时按协议使用 Markdown 交接，明确验证能力限制。不能以“已写报告”代替真实验收，也不能让用户自己填状态文件。

## 平滑交接

到已授权发布目标为止；交付维护、回滚和再次发布入口，不擅自创建持续后台任务。

本轮交付成果后必须结束，按上面的强制阶段停顿等待真实评审。用户在后续回复明确通过当前版本后，才读取下一阶段 SKILL.md，沿用工作流、AC 和已确认决定，先讨论下一阶段方案。阶段未完成时留在本阶段修订或记录 blocker，不把阻塞包装成完成。

## 必须执行的方法编排

开始本阶段时读取 [本阶段方法编排](references/methods.md)，按适用条件选择并实际读取、应用内置方法及必要引用。底层 Skill 的选择由 Stagecraft 承担，不把方法列表交给用户挑选。关键产品方向仍由用户确认。

方法编排规定执行顺序、每种方法的触发条件和验收产物；报告记录方法来源/版本、应用原因、具体产物与验证证据。只说“使用了最佳实践”或只读方法名不算完成。跳过不适用方法要说明原因，缺少必需能力则明确阻塞或覆盖限制。上游版本和许可证见 [来源清单](references/upstream/sources.json)，技术专项方法见 [技术栈映射](references/upstream/technology-skills.json)。
