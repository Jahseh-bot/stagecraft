# 发布与运维交接详细工作指引

## 发布输入与目标

确认实际发布对象、代码/构建版本、测试评审结论、账号/项目、环境、域名与访问范围、资源预算和用户授权。优先复用已有平台，不能因为某个方法更方便就换云或强加容器。仅本机预览不自动扩大成公网发布。

## 发布准备清单

| 方向 | 需要查验和保存的内容 |
| --- | --- |
| 可复现制品 | 来源提交/未提交变化、构建命令、运行时版本、锁文件、制品标识或摘要 |
| 环境配置 | 开发/预发/生产差异、变量名称、凭据配置方式、区域、访问控制；不记录密钥值 |
| 目标能力 | 静态/动态后端、存储、网络、TLS/DNS、跨域、资源/额度、平台限制 |
| 数据迁移 | 兼容窗口、迁移顺序、备份/恢复能力、校验、失败停止条件；不能假定回滚代码会回滚数据 |
| 发布策略 | 直接替换、滚动、灰度或其他实际可行方式的取舍；不为小项目强建复杂体系 |
| 健康验证 | 新版本身份、进程/依赖健康、关键用户路径、适用的指标与观察窗口 |
| 回滚与恢复 | 触发条件、可恢复版本、操作步骤、数据影响、验证与所需权限 |
| 运维交接 | 日志/监测入口、告警处理、后续更新、备份恢复、资源费用与关闭方法 |

查平台当前官方文档，验证必要配置与构建。缺少凭据或权限先完成可做准备并说明所需动作，不伪造上线。域名/账单等人工事项给具体操作，避免让用户研究一堆术语。

## 两次评审

发布前展示可审阅的清单、版本、目标、已知风险和回滚方案，用户确认具体计划后再进行外部变更。既有明确对同一计划的批准可以引用；不能拿抽象“上线”要求掩盖新费用、不同目标或数据变更。

发布后展示实际地址/版本、健康和关键路径证据、剩余限制及运行交接，用户评审这次结果后才完成阶段。两者不能互相替代。

## 执行与验证

记录执行命令或平台操作、时间、目标与响应。API超时或进程中断时先检查操作是否已生效，避免重复创建资源、重复迁移或重复发版。

区分构建成功、上传成功、流水线成功与服务真实可用。核对目标服务运行的是本次版本，再验证关键路径和适用依赖；不能以旧版本健康冒充新发布成功。公网不可访问时检查真实错误，不仅检查本地。

发布失败保留日志与当前实际状态，有限诊断修复；满足已批准回滚条件时执行并验证，否则先说明取舍并取得所需决定。回滚成功仍应报告本次发布失败。数据库恢复与代码回滚分开判断。

## 发布后与持续交付

交付运行手册：如何访问、查看日志、重启/更新、定位异常、回滚、恢复数据、停止服务和管理临时资源。若存在自动流水线，说明触发路径、环境、权限和制品来源，验证它实际运行的结果；未请求时不建立长期监控或后台任务。

用户后续修改上游材料时记录线上版本不变及影响评估，按新评审计划重发；不能自动将文档版本等同部署版本。未解决的线上风险与人工事项有具体恢复入口和责任边界，不以“已交接”掩盖仍然失败的服务。
