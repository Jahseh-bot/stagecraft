# 产品规划草案

日期：2026-10-20。状态：用户已授权按推荐方案实施；候选细节按本轮默认值落地，尚未验证的效果不视为已实现。

## 已确认的方向

用户希望发布一系列 npm 包，覆盖创意判断、产品到测试的研发链路。一个包承担一个职责，在适合的阶段安装 Skills；每个包可独立闭环，开发者可以只使用任意一个阶段。最终价值是加快产品开发。

## 建议的产品定位

面向 AI 编程的自动交付系统：接收任意阶段的材料与目标，澄清必要决策后自动执行所需阶段，验证结果并在必要时请求人工介入。阶段包是能力模块，用户不必逐个手工推进。

首批目标用户按推荐方案定位为使用 AI 编程工具的独立开发者和小团队。部署阶段已纳入首批工作流初版；首个参考流程为 Docker Compose 单机部署。持续生产运维和增长反馈不自动纳入首版范围。

## 候选包边界

| 阶段包 | 可接受输入 | 建议成果 | 需要明确的边界 |
| --- | --- | --- | --- |
| discover | 想法、问题、目标用户 | 证据、假设、实验、继续或停止建议 | 调研结论不能代替实际用户验证 |
| spec | 想法、外部文档、现有产品 | 范围、场景、验收标准、待决策事项 | 是否接受只有代码的输入 |
| design | 需求、截图、现有页面 | 用户流程、界面状态、交互方案 | 原型、图片、代码是否属于交付物 |
| architect | 需求、现有仓库 | 边界、接口、数据模型、技术决策 | 仅方案还是包含技术验证 |
| build | 需求、任务、已有仓库 | 代码变更、验证结果 | 无规格时补齐多少需求 |
| test | 仓库、运行地址、访问条件 | 测试、运行证据、缺陷与覆盖缺口 | 发现缺陷是否自动修改业务代码 |
| deploy | 已有项目、目标环境、必要访问条件 | 部署配置、发布记录、健康检查证据、失败诊断与回滚方案 | 支持平台、生产发布授权、数据库迁移及自动回滚边界 |

## 建议的接入规则

1. 有本体系产物：检查适用范围和时效，再复用。
2. 有外部产物：提取当前阶段必要信息，不要求迁移全部文档。
3. 只有代码或应用：区分观察到的事实、推断和用户要求。
4. 缺少关键输入：提出最少必要问题；无法验证的内容保持明确状态。

本轮采用这些接入规则；缺少关键输入时报告具体阻塞，允许交付明确标注的部分成果，不伪造验证。

## 建议的闭环定义

输入检查 → 必要澄清 → 执行 → 验证 → 成果与证据。

闭环不默认等于成功。建议允许“完成、部分完成、阻塞、失败”四种结果，并记录原因。测试包默认交付测试与缺陷；仅在用户要求修复时扩展到业务代码修复。

## 核心验收场景

- 空目录只有一个想法：discover 能完成创意判断，无须安装开发包。
- 只有外部 PRD：spec 能读取并识别缺口，无须重新走创意评估。
- 已有仓库与明确变更：build 能接手并遵守既有约束。
- 只有应用地址：test 在访问条件允许时工作，并说明无法覆盖的层级。
- 没有 PRD：测试不得把当前实现自动当作业务正确性的标准。
- 只有已有项目需要部署：deploy 可直接接手，不要求安装 build 或 test；执行必要的构建与发布检查不等于要求采用其他阶段包。
- 发布命令成功但健康检查失败：不得报告部署成功，需交付诊断与恢复建议。
- 涉及不可逆数据迁移：不得把代码回滚描述为整个系统已恢复。
- 仅安装一个包：不因缺少其他阶段包而失败。
- 依次使用多个包：复用有效产物，不重复询问已确认信息。

## 效果评估

比较原生 Agent、适合该场景的现有工具与本项目，固定任务、模型、运行环境和验收标准，重复运行并保留失败记录。

记录首次合格成果耗时、人工纠正次数、验收通过率、缺陷、调用成本，以及无证据宣称完成的次数。具体门槛在基线实验后制定，不预先承诺提升倍数。

## 初版交付边界

七个阶段包具备独立安装器、技能与模板；新增 runner 实现 PRD 澄清、方案确认、自动实现、真实验收、有界修复、人工介入和阶段恢复。支持固定上游 Skills 的来源配置与快照。已完成一个真实本地应用的纵向演练；其他入口、通用任务图和生产部署仍未实现。详见架构和路线文档。

## 用户澄清后的核心验收

- 输入 PRD，确认关键决策后，无须人工逐阶段发指令即可交付本地可运行版本。
- 只在关键决策、权限、外部依赖或失败预算要求时介入，普通执行细节自动推进。
- 中断或人工等待后可恢复，保留决策与执行证据。
- 从已有项目的测试或部署进入时，跳过不需要的前序阶段。
- 自动推进以约定目标和真实验收为依据，不能凭自然语言“完成”跳过验证。
