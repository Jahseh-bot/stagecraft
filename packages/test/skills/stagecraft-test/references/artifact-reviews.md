# 阶段产物、评审与变更管理

在各阶段开始、交付评审、恢复和修改已确认成果时读取。本规范组织真实工程中的需求、设计、技术、开发、测试和发布评审；按项目风险裁剪材料深度，不伪造团队、签字或宣称符合所有公司的同一标准。用户决定方向和验收，agent 承担专业分析、执行与证据整理。

## 每阶段可见的交付物

| 阶段 | 保存到项目的主要成果 | 展示和评审重点 | 后续输入 |
| --- | --- | --- | --- |
| discover | 产品机会说明、场景、价值假设、验证计划 | 目标用户、问题证据、MVP取舍与未知项 | 产品边界和验证假设 |
| spec | PRD、用户流程、业务规则、AC验收矩阵、非目标 | 完整PRD可打开；演示核心场景、异常路径与范围 | 产品和设计基线 |
| design | 信息结构、交互稿、实际设计稿/原型、组件与状态说明 | 展示可见设计预览及源文件；桌面/移动端、空/错/加载状态；不能只写设计文字说明冒充设计稿 | 已评审设计和交互契约 |
| architect | 技术方案、架构/数据/接口设计、ADR、任务与验证计划 | 架构图、关键取舍、成本、依赖、失败恢复和风险 | 实现契约与任务分解 |
| build | 代码改动、可运行版本、演示与启动方法、自测结果 | 展示运行效果/差异，关联AC与设计；执行代码检查并说明尚未覆盖内容 | 被测版本与可复现环境 |
| test | 用例集、覆盖映射、逐例结果、缺陷/回归报告 | 执行前评审用例与范围；执行后展示通过/失败/未测及证据 | 质量结论与剩余风险 |
| deploy | 发布清单、变更/版本、目标、回滚方案；发布后地址与验证/运维交接 | 实际发布前评审具体版本、目标、测试结论与回滚；发布后展示可访问结果、健康及关键路径 | 发布记录与后续维护入口 |

非UI产品可说明设计稿不适用并评审相关交互/接口契约，不虚构界面。用户只要求某一阶段时仅交付该阶段。直接从已有项目进入时，检查现有输入并记录基线；缺失前置产品决定或评审时补足相关材料，不编造上游完成。

## 项目目录与版本

优先沿用项目已有 docs、design、tests 等约定；没有约定时可使用：

```text
docs/stagecraft/<workflow-id>/
  index.md                 # 可点开的产物目录与当前状态
  product/PRD.md
  design/                  # 源文件、预览、交互说明
  architecture/            # 技术方案、ADR、任务计划
  qa/                      # 用例、执行结果、缺陷
  release/                 # 发布清单、回滚、交接
.stagecraft/workflows/<id>/
  workflow.json
  <stage>-report.md
  reviews/<stage>/<submission-id>/files/  # 助手保存的提交快照
  reviews/<stage>/<submission-id>/review.json
```

这是推荐布局，不强制搬迁已有文件。代码保留正常源码目录。外部设计工具/托管链接同时记录源对象ID、版本和可合法导出的预览/说明到项目；无法导出时明确限制，不只留一个可能失效的URL，不声称已完整归档。不要把凭据或真实用户敏感数据复制进快照。

产物目录记录稳定产物 ID、当前路径、阶段、修订/提交 ID、状态、上游依赖、评审记录与验证证据入口。PRD需求使用 AC，设计节点、ADR、任务、TC、缺陷和发布记录通过 ID/路径连接。目录与 workflow 是会变动的索引，不作为自身提交的不可变证据。只有Git哈希不足以替代未提交文件版本；快照与哈希保存当次评审内容。

## 展示 → 评审 → 修订 → 基线

1. 完成当前环节约定成果和自检，保存项目文件。先展示成果：文档给可点开路径及重点；设计给实际图片/原型预览；代码给可运行演示和主要变化；测试给具体用例/结果；发布给清单或访问地址。宿主能打开文件/预览就主动打开；不能展示时给可打开路径和步骤，如实说明限制。
2. 显示本次版本、相对上版变化、验收依据、已知限制、需要用户评审的要点。用户必须能看到实际产物，不能只报告“已完成”。此处只交付当前阶段，下一阶段只说明名称，不提前产出方案或成果。
3. 提交评审，状态为 awaiting_review。展示后用最终回复结束当前轮，停止工具调用；禁止同轮自行记录通过或推进下一阶段。第一个选项是 agent 根据实际质量最推荐的处理方式并说明理由；如成果有关键缺口，应推荐修改而不是默认推荐通过。提供其他合理处理方式及自由文字意见入口。先前同意方案不等于批准尚未看过的成果；沉默、超时、默认选中都不是通过。
4. 用户要求修改时记录具体意见与影响的产物/AC。明确意见直接落实；有歧义或冲突时先讨论方案。修订、自检、展示差异后重新提交，保留旧快照与反馈，不覆盖历史或把旧批准套到新版。再次结束本轮等待新版评审，“修改后继续”也不能提前批准修改结果。
5. 在展示该版本并结束交付轮之后，收到用户明确通过具体版本的真实回复后记录真实回复及会话/评审来源，完成该阶段并作为下游基线。已对相同未变化成果作出的明确评审可引用，不重复索要批准。只能记录实际发生的评审，不能伪造用户意见或把 agent 自评当用户评审。

阶段 `completed` 同时意味着约定产物就绪、必要验证成立、对应版本评审通过。测试完成但用户未评审，只能报告“验证完成，待评审”。仅分析/只读任务同样展示并评审分析成果，不自动授权实施。

中间门禁也必须执行：测试用例在测试执行前展示评审；发布清单在外部发布前展示评审。它们可以保存为同一阶段的评审材料，不新增虚构阶段。阶段最终评审不能倒过来充当已经执行的发布授权。

## 随时修改与下游影响

收到修改意见时先读取[全链路变更联动](change-control.md)，定位对应成果及当前基线。按需求、设计、技术/任务、代码、用例/测试、文档与发布之间的双向关联列出受影响与不受影响项；本助手的线性依赖采用保守失效，不能因声称不受影响跳过被标 stale 阶段的重新检查。

将变更记录保存到项目：原因、用户原话/来源、旧/新提交ID、受影响AC/文件/测试/发布、需要重做和重新评审的部分。先停止依赖旧成果的新执行；允许不依赖该变化的工作继续。上游重新评审后，逐个核对/修订受影响下游，重新验证并确认有效版本。不静默更新旧哈希来伪装旧证据仍然有效。

线上版本不会因为文档变化自动回滚或重发：先评估真实影响，再按用户已授权的发布/回滚范围处理，保存实际部署版本与验证结果。修订评审不代表对新的外部操作自动授权。

## 交接助手的约束与局限

新助手使用 v2：begin → submit → review → complete。submit 接收成果/验证 receipt，保存内容快照并进入 awaiting_review；review 记录真实用户反馈（approved 或 changes_requested）；complete 只接受已批准且文件/证据/快照未变化的当前提交。修改请求后 begin 开始修订，再 submit 生成新提交。

review 输入由 agent 根据实际回复生成，不要求用户写JSON：

```json
{
  "submission": "submit返回的currentSubmission",
  "decision": "approved",
  "reviewer": "user",
  "source": "实际会话消息标识或评审来源",
  "comment": "用户对本次版本的实际回复",
  "presented": ["实际展示的文件/预览及其版本"]
}
```

工具校验状态、文件和记录结构，不能独立证明用户身份、回复真实性或预览确实被看过；agent 必须忠实记录。旧 v1 工作流首次打开会备份旧状态并保守标记已有工作待重新检查/评审，不删除旧文件，不虚构过去已经评审。没有 Node 时用等价 Markdown 目录、版本副本、评审记录与状态实现同样门禁，说明缺少自动哈希检查。

变更矩阵必须记录每个受影响真实文件、设计源/预览、用例预期与教程的同步状态；标记stale只是暂停旧依据，不是修改完成。从测试发现的问题也必须反查需求与设计。统一变更规则、工具和模板见[全链路变更联动](change-control.md)。
