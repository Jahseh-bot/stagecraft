# 测试用例设计与评审

在测试执行前使用。本技能由 stagecraft-test 自动读取，无需另装；只要求设计用例时，到评审后的用例集交付为止，不自动运行测试或修改业务代码。读取本目录 [设计方法](methods.md) 和 [用例与执行模板](assets/casebook.md)。方法参考与原创适配边界见 [来源说明](sources.md)。

## 1. 讨论测试范围与方案

读取 PRD、已确认 AC、设计/接口契约、当前版本、既有用例和实际可得的缺陷记录。记录文件与版本。已有测试是可复用资产，不是需求的唯一依据；不能把当前实现行为反过来当成预期。

先列 2–3 个适合当前任务的覆盖与执行方案，选项 1 始终为最推荐方案，解释风险覆盖、时间成本和局限；最后邀请“如果都不合适，可以直接输入你的想法、约束或组合方案”。例如小型改动可比较核心行为与相关回归、完整版本回归、仅用例审计；按任务调整，不硬套选项。用户决定覆盖目标、业务规则、环境和风险取舍，agent 选择具体设计方法。已有明确选择或委托注明来源并复用，不能以默认选中、沉默或超时代替回答。

需要时读取 methods.md 的复杂任务补充，覆盖多角色、数据任务、AI和多端；只展开产品实际支持的能力。维护既有用例时保留编号与替代关系，不能整批重写后丢失历史追踪。

## 2. 拆解测试点

以需求/AC 为根，生成稳定 TP 编号，按正常/分支行为、输入边界、异常恢复、业务规则/状态、适用的非功能风险拆点。每个测试点连接来源与风险，不用凑数量。缺少预期规则时记录问题 ID 和受影响 TP/TC，先与用户讨论；例如数量上限、重试语义、响应时间门槛不能自行发明。无关部分可继续。

## 3. 展开可执行用例

逐点生成或复用稳定 TC 编号，填明前置条件、具体数据、操作顺序、可观察预期、优先级、执行层级/方式和清理方法。保持 AC → TP → TC → 脚本/人工步骤的映射。默认采用模板中的 Markdown；需要机器处理时使用等价 JSON，已有团队模板优先。用户需要 Excel/XMind 时先检查能力并核验实际文件；不能把改扩展名的文本当原生文件，也不能让导出工具成为执行的强制依赖。

设计预期先于执行；未执行用例一律记 not_run。复用已有自动化测试时必须检查断言是否确实覆盖该 TC；只运行整套测试而没有用例映射，不代表所有新用例均已执行。

## 4. 补齐遗漏与评审

应用设计方法中的风险检查，优先覆盖本次变化和真实历史缺陷。补充用例保留原 ID 和来源、补充原因；没有历史记录就注明未提供，不虚构历史故障。

按需求一致性、可执行性、预期可验证性、风险价值和重复性评审，分类 ready / needs_revision / excluded。修正可自行澄清的表达与数据问题；业务歧义提选项和推荐理由，等待回复，不代改需求。去重保留原 ID、替代 ID 和原因，不悄悄删除高风险用例。审阅具体内容，不能只用数量、评分或字段齐全代替质量判断。

向用户呈现覆盖范围、代表性核心/异常用例、遗漏与待决问题、执行成本。用例集必须保存到项目并展示给用户评审，具体版本明确通过后才能执行；已有真实评审覆盖同一未变化版本时说明依据，不逐条重复问。方案确认不能替代用例产物评审。只执行 ready 且处于已确认范围的用例。重要用例未就绪时可执行无依赖用例，但总体状态必须 partial/blocked。

## 5. 交给测试执行并闭环

设计交付包括用例集版本、需求覆盖映射、评审记录、未决问题及执行计划。stagecraft-test 随后按 TC 执行，记录版本、环境、实际结果、证据和缺陷 ID。用例评审 ready 与执行 passed 是不同状态；只有实际观察或断言验证才可 passed。

失败后保留原记录，授权范围内诊断修复，再执行原失败用例和受影响回归；新发现的场景先补用例并评审，再执行。新的业务取舍或范围变化先与用户讨论，确认后更新用例版本和相关 AC。需求/代码/环境改变使关联旧结果失效，不能沿用旧 passed 冒充新版本验证。

统计时给出明确分母：约定范围内 AC 总数、具有 ready 用例的 AC 数、实际验证通过的 AC 数；分别报告 TC 的 passed/failed/blocked/not_run/skipped。excluded 是设计评审分类，不计入通过率；skipped 须说明原因和风险接受来源。存在未覆盖 AC、关键未执行用例或阻断缺陷时，不给出无条件可发布结论。
