# 创意判断

在当前 coding agent 中直接完成本阶段，不启动嵌套模型或要求用户操作 runner。先阅读本技能内的 [统一执行与交接协议](references/protocol.md)，它定义自主决策、有限修复、授权边界与跨阶段恢复。用户目标与项目约定优先；不要求安装其他阶段技能。

## 接手与恢复

识别用户的目标、当前项目、入口与终点。已有匹配工作流时读取交接记录、真实成果和验证证据，复用已确认决定；输入改变则重新检查相关结论。没有上游成果时补足本阶段必需输入即可开始，不为凑齐七阶段而要求重复采访。

## 每个阶段与环节的方案讨论

目标人群、核心问题、产品定位及 MVP 方向。先给不同定位或验证路径及证据、投入和推荐理由；用户选择后才能把建议当成后续产品方向。仅要求调研时可以交付建议，不代替用户决定立项。

每个阶段开始时先讨论本阶段方案；每个涉及选择的环节执行前，列出 2–3 个实际可行的选项，第一个始终是 agent 最推荐的方案，并解释推荐理由、适用条件与取舍。最后始终提示“如果都不合适，可以直接输入你的想法、约束或组合方案”。等待用户实际回复后再执行依赖该选择的工作；默认选中、沉默和等待超时都不算确认。已有明确选择直接复用，说明依据；用户明确委托的范围按委托执行。

遵循统一协议的决策门槛：先给具体方案和推荐理由，等待用户选择确认；记录决定及来源。用户已明确选择或明确委托的范围直接复用，不重复确认。待确认时只推进无依赖的调研或方案预览，不实施依赖该选择的成果。

## 覆盖范围与详细操作

开始工作时读取 [跨阶段覆盖与裁剪](references/coverage.md)，建立本任务适用性矩阵，再读取 [本阶段详细工作指引](references/stage-guide.md) 中对应环节。逐项记录适用、不适用或未知的依据，把适用检查连接到具体产物、验证和评审；不能把清单勾选当成已验证。项目越小材料越精简，但不省略有实际风险的环节。

宿主工具不同或三方引用缺失时，读取 [三方只读适配说明](references/upstream-adapters.md)。第三方方法只读：不修改或删除其原始文件、示例与许可证。宿主适配和覆盖补充写在自研层，按当前任务读取匹配方法；缺少专项能力明确说明，不假装通用流程已经完成专项审查。

## 执行闭环

1. 从用户目标、现有材料和项目记录识别目标人群、痛点、替代方案与决策期限。先检查可查证事实；仅对会改变研究方向的缺口提问，不把所有采访问题都交给用户。
2. 有联网能力时调查一手产品、公开定价、文档和用户研究，保存链接、访问日期、支持的具体主张与反证。没有联网能力时明确证据限制，不能把推测写成市场事实。
3. 拆分价值、实现、分发、付费等假设，按影响与不确定性排序。提出最小验证实验，写明对象、成本边界、操作、观察指标和继续/停止阈值的依据。实际对外联系或付费实验须有相应授权。
4. 根据已取得证据给出 go / validate-first / no-go 建议、置信限制及可推翻结论的条件。小范围证据不足时自主缩小主张，补充可取得资料，再审查结论是否仍成立。
5. 逐条检查关键主张能否追溯到证据，实验是否能区分相反假设、MVP 是否解决最核心问题。修正矛盾后提交发现报告；研究执行完整可完成本阶段，但不能声称尚未执行的市场实验已验证需求。

## 产物展示与用户评审

遵循 [产物、评审与变更规范](references/artifact-reviews.md)，将本阶段实际成果存入项目并更新产物目录；主动展示可打开的文档、可见设计预览、运行演示或验证结果。提交具体版本供用户评审，记录反馈，按意见修改、自检并重新展示差异。方案确认不能替代成果评审；当前版本未经用户明确通过，不标 completed、不执行依赖它的下游工作。任何时候收到修改意见，都保留旧快照与评审记录，分析并重新验证受影响下游。

## 本阶段交付与验收

交付：目标用户与问题陈述、证据矩阵、假设优先级、MVP边界、验证实验和决策报告。

完成条件：关键主张有来源或清楚标为假设；至少分析一个替代方案和反证；实验有可执行步骤及判断标准；建议与证据强度一致。

使用 [报告模板](assets/report.md) 保存目标、AC、成果、实际证据及剩余问题。用 [交接助手](scripts/handoff.mjs) 记录阶段；无 Node 时按协议使用 Markdown 交接，明确验证能力限制。不能以“已写报告”代替真实验收，也不能让用户自己填状态文件。

## 平滑交接

spec：把决策报告中的已支持需求转成可验收规格；保留 validate-first 条件。

用户授权继续且下一技能可用时，在同一 agent 中直接读取下一阶段 SKILL.md，沿用同一工作流、AC 标识与已确认决定。先解决本阶段尚未确认的关键选择并完成产物评审，当前成果通过后，自动准备下一阶段方案供用户讨论选择，未确认前不执行依赖该方案的工作；即使 agent 有能力选定，也不代替用户决定关键方向。阶段未完成时先修复或准确记录 blocker，不能把阻塞状态包装成完成后传下去。

## 必须执行的方法编排

开始本阶段时读取 [本阶段方法编排](references/methods.md)，按适用条件选择并实际读取、应用内置方法及必要引用。底层 Skill 的选择由 Stagecraft 承担，不把方法列表交给用户挑选。关键产品方向仍由用户确认。

方法编排规定执行顺序、每种方法的触发条件和验收产物；报告记录方法来源/版本、应用原因、具体产物与验证证据。只说“使用了最佳实践”或只读方法名不算完成。跳过不适用方法要说明原因，缺少必需能力则明确阻塞或覆盖限制。上游版本和许可证见 [来源清单](references/upstream/sources.json)，技术专项方法见 [技术栈映射](references/upstream/technology-skills.json)。
