# Stagecraft 零基础使用教程


## 什么是 Stagecraft

Stagecraft 把产品探索、需求、设计、架构、开发、测试和部署的方法，组织成七个可在 coding agent 中调用的 Skills。你负责产品方向和成果评审，agent 根据阶段选择内置方法，完成执行、验证和交接。

你不用研究底层几十个 Skills 该如何搭配，也不用在终端填写答案 JSON。所有讨论都发生在你正在使用的 agent 会话里，成果和记录保存在项目文件夹中。

## 先选适合你的路线

| 你现在有什么 | 从哪里开始 |
| --- | --- |
| 从没用过终端或 coding agent | [准备环境](./preparation)，再跟着[第一个任务](./first-run)做 |
| 只有一个产品想法 | [创建需求说明](./requirements)，让探索与规格阶段先补齐 |
| 已有 PRD，想做成产品并上线 | [从 PRD 到交付的完整提示词](./first-run#prd-to-deploy) |
| 已有代码，只想检查或修复 | [已有项目测试与修复](./existing-project) |
| 已安装旧版 | [更新与迁移](./upgrading) |

## 你会经历什么

**讨论方案 → 选择方向 → 执行与自检 → 展示产物 → 评审修改 → 衔接下一阶段。**

每个尚未确定的决策环节会给出可行选项，第一个是推荐项并解释原因，你也可以自由输入自己的要求。已经确认的决定会复用；确认范围内的实现细节和修复由 agent 继续完成。

方案通过和成果通过是两件事。比如你选了设计方向，agent 做完后仍要给你看实际设计稿；你评审通过具体版本后，才把它作为开发依据。详见[方案讨论](./confirmation)与[产物评审](./artifact-reviews)。

## 当前应该安装哪一版

本教程对应 **Stagecraft 0.4.1**，已于 2026-10-21 发布全部八个 npm 包，包含阶段评审、用例设计及最近的方法升级。可以从 GitHub 安装，也可以通过 npm 阶段包固定到 0.4.1。

现在在目标项目目录使用：

```sh
npx skills add Jahseh-bot/stagecraft
```

这是通过 npm 运行通用安装工具，再从 GitHub 获取 Stagecraft Skills。完整操作及 npm 固定版本命令见[技能安装](./packages)。安装不会提供模型账号、额度或云服务器；执行使用你当前 agent 的账号、工具和权限。

## 准备环境

本教程使用 GitHub 上的最新 Skills。准备 Node.js、Git，以及一个能操作项目文件和运行命令的 coding agent 即可。

## 第一步 打开终端

macOS 按 Command + 空格，搜索“终端”；Windows 打开 PowerShell；Linux 打开终端。下面标为 sh 的内容都在这里执行，一行复制一次，按回车运行。不要复制提示符 `$`、`%` 或 `➜`。

稍后标为 text 的提示词要发给 agent 的聊天输入框。**终端执行命令，agent 对话框讨论产品和回答问题。**

## 第二步 安装并检查 Node.js

从 [Node.js 官网](https://nodejs.org/) 安装满足 **22.20.0 或更高版本**的版本，安装完成后重新打开终端：

```sh
node --version
```

例如 `v22.20.0` 满足要求，`v22.0.0` 不满足本教程所用通用 skills CLI 的要求。再分别检查随 Node.js 安装的工具：

```sh
npm --version
npx --version
```

三条命令都应显示版本。若提示找不到命令，重开终端；仍失败再检查安装路径。版本要求依据 [skills CLI 官方说明](https://github.com/vercel-labs/skills)。

## 第三步 安装并检查 Git

从 [Git 官网](https://git-scm.com/downloads) 安装适合系统的版本，重开终端后运行：

```sh
git --version
```

看到 `git version ...` 即可。Git 用来获取技能来源。安装公开 Stagecraft Skills 不需要登录 GitHub，也不需要手动克隆整个 Stagecraft 仓库；以后把自己的产品推送到 GitHub 时，才需要相应账号和仓库权限。

## 第四步 准备 coding agent

打开已有的 Codex、Claude Code、Cursor、Copilot、Gemini CLI 或 OpenCode，完成该工具自身的登录。它需要能读取与编辑目标项目，并按任务运行测试和构建。

无需为 Stagecraft 另装 Codex CLI。只有聊天、不能操作文件的工具无法独立完成编码和验证。宿主没有自动发现 Skills 时，可以明确让它读取安装目录的 `SKILL.md`。

## 第五步 创建你的产品文件夹

在桌面或你习惯的位置创建 `my-app` 文件夹。它用于存放你的产品，和 Stagecraft 源码仓库是两个概念。用 coding agent 的“打开文件夹/项目”功能打开它，再在终端进入同一个文件夹：

```sh
cd "/替换为你的项目完整路径/my-app"
```

路径需要改成你电脑上的实际位置，不要原样复制占位符。Windows 可以使用 `cd "C:\Users\你的用户名\Desktop\my-app"`。路径含空格时保留双引号。

完成后继续[安装技能](./packages)或[开始第一个任务](./first-run)。首次安装需要能访问 npm 和 GitHub。

## 阶段包与技能安装

## 推荐：安装当前 GitHub 版本

先完成[环境准备](./preparation)，在你自己的产品目录执行：

```sh
npx skills add Jahseh-bot/stagecraft
```

1. npm 若询问是否下载 skills 工具，确认后等待下载。
2. 安装界面列出 Skills 时，完整产品流程请选择下面的七个 `stagecraft-*` 入口。测试用例子技能已经包含在 test 中，不必另选。
3. 选择实际使用的 coding agent；若询问安装范围，新手选当前项目。
4. 按界面提示完成安装，记下输出的技能目录。
5. 回到 agent 打开同一个项目，重新加载 Skills 或新建项目会话。

安装完成只表示技能文件已就位，**还没有开始写产品**。下一步需要发送[任务提示词](./first-run#prd-to-deploy)。

## 七个入口的分工

| Skill | 工作与主要成果 |
| --- | --- |
| stagecraft-discover | 判断用户问题与产品机会，比较 MVP 和验证方向 |
| stagecraft-spec | 形成 PRD、业务规则、术语与验收标准 |
| stagecraft-design | 产品流程、页面状态、视觉方案与实际预览 |
| stagecraft-architect | 技术方案、数据与接口契约、实施顺序 |
| stagecraft-build | 实现、自测、修复与可运行交付 |
| stagecraft-test | 先设计与评审用例，再执行、记录缺陷和回归 |
| stagecraft-deploy | 发布前评审、实际部署、访问验证和回滚交接 |

完整流程推荐一次装齐七个入口，agent 根据已有成果选择从哪里开始，不会强制重复所有阶段。单点任务也可以只装需要的阶段。

## 已知道技能与 agent 时

只安装测试入口：

```sh
npx skills add Jahseh-bot/stagecraft --skill stagecraft-test
```

为 Codex 安装全部七个入口：

```sh
npx skills add Jahseh-bot/stagecraft --skill stagecraft-discover stagecraft-spec stagecraft-design stagecraft-architect stagecraft-build stagecraft-test stagecraft-deploy --agent codex
```

通用 CLI 中 Claude Code 使用 `--agent claude-code`，Cursor 使用 `--agent cursor`。不确定宿主标识就用第一条交互式命令选择。其他选项以 [skills CLI 官方说明](https://github.com/vercel-labs/skills)及安装输出为准。

## 确认 agent 能读取

在 agent 对话框发送：

```text
请检查当前项目可用的 Stagecraft Skills。
列出已找到的七个阶段入口及实际路径，读取各入口说明。
本次只检查安装，不开始开发；缺少哪个入口请明确告诉我。
```

Codex 的常见项目路径是 `.agents/skills/stagecraft-build/SKILL.md`。其他宿主以安装器输出为准，不要盲目复制 Codex 的目录。宿主支持的目录适配不等于所有模型和环境都经过完整实机验证。

## npm 安装：固定到 0.4.1

2026-10-21，全部八个 `@gaaraa/*@0.4.1` 已发布。想固定方法版本，可以使用七个阶段包的安装器。以下命令在你的产品项目目录执行，示例使用 Codex；替换为自己的宿主即可。

```sh
npx --yes @gaaraa/discover@0.4.1 init --agent codex --dir .
npx --yes @gaaraa/spec@0.4.1 init --agent codex --dir .
npx --yes @gaaraa/design@0.4.1 init --agent codex --dir .
npx --yes @gaaraa/architect@0.4.1 init --agent codex --dir .
npx --yes @gaaraa/build@0.4.1 init --agent codex --dir .
npx --yes @gaaraa/test@0.4.1 init --agent codex --dir .
npx --yes @gaaraa/deploy@0.4.1 init --agent codex --dir .
```

这里的 `.` 表示当前目录，先确认终端已经进入你的产品文件夹。七条命令分别安装对应阶段，不会自动开始产品开发。已有相同技能时无需重复安装；发生不同内容冲突，先备份原技能与自定义修改，再把旧目录移出宿主扫描位置后重新安装。

| npm 安装器的 --agent | 项目内技能目录 |
| --- | --- |
| codex / generic | .agents/skills |
| claude | .claude/skills |
| cursor | .cursor/skills |
| copilot | .github/skills |
| gemini | .gemini/skills |
| opencode | .opencode/skills |

注意：npm 阶段安装器用 `--agent claude`，通用 skills CLI 用 `--agent claude-code`，两种工具的参数不同。npm 安装器支持 `--dry-run` 预览，或用 `--skills-dir` 指定自定义目录（与 `--agent` 二选一）。GitHub 与 npm 安装方式选一种即可。

只运行 `npm install @gaaraa/build` 会下载包到 node_modules，不等于宿主已经发现技能。新项目无需安装兼容用的 `@gaaraa/runner`。安装后重新加载 agent，发送[完整提示词](./first-run#prd-to-deploy)。更新方法见[版本与迁移](./upgrading)。

## 创建需求说明

## 用普通话描述你要的结果

你可以在 agent 会话里直接描述，不强制先写 PRD。需求复杂时，在目标项目新建 `PRD.md` 文本文件，写清楚给谁使用、主要功能、范围和完成标准。

例如：

```md
# 温度换算网页

给普通人使用，中文界面，适配电脑与手机尺寸。
输入摄氏度或华氏度，显示另一种温度，保留一位小数。
支持清空；空值和非法数字显示中文提示。
只在本机运行，不需要账号、数据库、支付或外部 API。
验收：0℃ = 32.0℉；100℃ = 212.0℉；32℉ = 0.0℃。
请实际运行测试，给出本地启动命令和浏览器地址。
```

第一次不要把真实密码、Token、私密业务数据写进需求。需要外部服务时使用宿主已有的凭据机制；敏感值不写进交接报告。

如果需求仍不清楚，可以先安装 `spec` 技能，让 agent 从现有材料补足可验收规则。它只会集中询问真正影响业务含义的缺口。

## 只有想法，没有 PRD

在安装七阶段 Skills 后，把下面内容发给 agent：

```text
使用 stagecraft-discover 和 stagecraft-spec，帮我把这个想法整理成可评审的 PRD。
我的想法：做一个中文温度换算工具。
先讨论用户、场景、首期功能和边界。每次给可行方案，推荐项放第一并说明理由，允许我自由补充。
沿用已有资料，不替我决定尚未确认的产品规则。
把 PRD、验收标准、决定和待决问题保存到项目，展示实际文件让我评审。
这次先停在 PRD 评审，不开始写产品代码。
```

PRD 评审通过后，使用[完整交付提示词](./first-run#prd-to-deploy)继续。只有范围确实适用时才进入设计与架构；已有资料不重复生成。

## 开始第一个任务

这一页带你做一个中文温度换算网页。先在终端安装，随后所有需求讨论、方案选择和成果评审都在 agent 会话中进行。

## 第一步：安装七个阶段

按[准备环境](./preparation)创建 `my-app` 并让 agent 打开它，在该项目的终端执行：

```sh
npx skills add Jahseh-bot/stagecraft
```

选择七个 `stagecraft-*` 入口以及你正在使用的 agent。完成后重新加载 Skills 或打开新项目会话。完整流程安装七个入口，避免到了设计或架构阶段才发现技能缺失；[安装详解](./packages)提供非交互指定方式。

## 第二步：放入 PRD.md

在项目文件列表中新建文件，命名为 `PRD.md`，粘贴并保存：

```md
# 中文温度换算网页

用户：希望快速换算温度的普通人。
功能：摄氏度与华氏度双向换算，结果保留一位小数，支持清空。
规则：空值和非法数字显示中文提示；清空后不能残留旧结果。
界面：电脑和手机尺寸均可使用，清晰易读。
范围：不需要账号、数据库、支付或外部 API。
验收：0℃ = 32.0℉；100℃ = 212.0℉；32℉ = 0.0℃。
尚未决定：输入方式、视觉风格、是否限制温度范围及上线平台。
先在本机预览，是否发布公网由我确认。
```

这是一份输入草稿，agent 需要讨论未决定项并提交正式需求评审。手机尺寸适配不等于真实手机可以访问你电脑，也不等于已经发布公网。

已有自己的 PRD 时直接放入项目，文件名不同就在下方提示词里改路径。还没有 PRD 时见[创建需求说明](./requirements)。

## 第三步：从 PRD 到完整交付 {#prd-to-deploy}

下面整段发给 **agent 的聊天输入框**，不要输入系统终端。默认先本机预览、发布前再讨论目标，因此不需要你提前懂部署平台。

```text
请使用当前项目已安装的 Stagecraft Skills，读取 PRD.md，把需求推进到可运行、经过测试和评审的产品。
先在本机预览。部署目标尚未确定：到发布阶段请给出可行选项、费用和限制，等我确认后再部署。
如果我已经在 PRD 或对话里明确了部署目标，请沿用并说明依据。

先检查项目、已有成果、七阶段 Skill 与方法编排，建立或沿用同一个 .stagecraft/workflows 工作流。
底层方法由你按任务选择并实际应用，不要让我研究几十个 Skills。
根据现有成果选择起点：
- 只有想法时用 stagecraft-discover 推敲用户问题和产品方向；
- 用 stagecraft-spec 完成 PRD、业务规则和可验证验收标准；
- 用 stagecraft-design 完成产品流程、页面状态和可查看的设计预览；
- 用 stagecraft-architect 比较技术栈与架构，形成接口、数据和实施计划；
- 用 stagecraft-build 实现已确认范围，实际运行、自测并修复；
- 用 stagecraft-test 内置的 stagecraft-test-case-design 先拆测试点、生成用例、补漏与评审，再逐例执行和回归；
- 用 stagecraft-deploy 准备发布清单、部署、验证本次版本与地址，并交付回滚方法。
已有真实、有效且已确认的成果直接复用；缺少必要输入先补齐，不为凑流程重做工作。

每个阶段开始与需要选择的环节，先给 2–3 个可行方案。
选项 1 是你最推荐的，解释理由及体验、成本、维护等取舍；最后允许我输入自己的想法或组合方案。
只有一种可行方案时说明原因。等我选择后再实施依赖该选择的部分。
不要把沉默、默认选中或你补写的假设当成我的确认。
复用我已经确认的决定和明确委托，选定范围内的实现细节、验证与修复自主完成。
新问题改变范围、产品规则、技术方向或发布风险时，重新讨论。

每个阶段把实际成果保存在项目，维护一个可打开的产物目录：
文档给路径，设计给真实预览，应用给运行效果；说明本版变化、自检结果和待评审重点。
我提出修改后保留旧版和反馈，修订并再次展示。
我明确评审通过具体版本后，才启动依赖它的下游工作。
测试用例先评审再执行；测试结果展示评审；发布清单先评审再上线，上线结果再次展示。
可以把当前成果评审与下一阶段方案放在同一条消息里，但分别记录我的决定。

保持需求、设计、代码、测试和发布的可追溯关系：
用验收编号关联测试点和用例，逐例记录实际结果、环境、版本与证据。
上游改动后标记受影响成果，重新验证与评审；不要沿用旧版通过结论。
不得通过删除有效测试、跳过断言或降低验收标准获得通过。
没有工具、权限、凭据或真实验证条件时，记录具体阻塞与下一步，不假装完成。
不要让我手写 JSON。

自动衔接是执行完已确认工作后准备下一环节的方案和交接，而不是替我做关键决定。
最后给出产物目录、实现范围、测试结果、未验证项、启动命令、实际访问地址和回滚方法。
```

如果已经知道目标，把第二段替换成自己的仓库、托管项目或服务器说明。例如“静态站点发布到我已授权的 GitHub 仓库 用户名/仓库名 的 Pages”。不要把密码或 Token 写进提示词；[部署教程](./deployment)介绍目标选择和验证。

## 第四步：回答方案，查看成果

agent 应先展示当前缺口、推荐方案和取舍。你可以回复：

```text
选 1，但输入方式改成两个可切换的方向。先给我更新后的 PRD 评审。
```

打开它给出的 PRD 文件，确认内容后再回复：

```text
这版 PRD 评审通过，可以进入设计；先给我两个设计方向和推荐理由。
```

不满意就直接描述修改，不必懂技术词汇。设计阶段要看到预览，开发阶段要能打开应用，测试阶段要看到用例和真实结果。只回复“继续”若无法区分是同意方案还是验收成果，agent 应澄清具体版本和动作。

## 第五步：拿到可验证的交付

完成时检查以下内容：

- 每条已确认需求有对应实现与验证，未做或未验证的内容单独列出。
- 本地应用有实际启动命令和地址，能亲自试用。
- 若要求公网发布，有真实地址、本次版本和关键路径检查；只有推送记录不算上线完成。
- 项目里能找到 PRD、设计、技术方案、用例、结果、发布记录和评审意见。

更具体的启动步骤见[查看成果](./delivery)。只想做到本机测试，可以明确说“本次终点为测试验收，不执行部署”。

## 中断后继续

安装 Skills 不会启动一个脱离会话的后台开发服务。会话结束、换 agent 或解决阻塞后，打开同一项目，发送：

```text
读取本项目 Stagecraft 的工作流、产物目录、评审和证据，继续 PRD.md 对应任务。
沿用已确认且仍有效的决定，展示当前待评审成果或待选择方案。
从中断处继续；上游有变化的部分先重新验证，不重做仍有效的工作。
如果有多个工作流无法区分，请说明差别让我选择。
```

没发现技能时，让 agent 读取安装输出中的实际 `SKILL.md` 路径。不要重新执行旧 runner 的 start 来恢复这个工作流；两者的记录不同。详见[恢复与处理失败](./resume)。

## 不再纠结选哪套 Skill

## 你专心做产品，Stagecraft 负责组合方法

做产品的难点不只是让 AI 写代码。需求、产品设计、视觉、架构、开发、测试和部署各有大量 Skills；挑哪一个、何时用、怎样衔接、如何判断它有没有真正起作用，本身就需要经验。

Stagecraft 把这些选择收进七个阶段入口：按任务筛选内置方法，组织执行顺序，传递成果，并要求实际验证。你不需要比较底层 Skill 清单，只需要说明要做的产品、选择关键方向、检查交付结果。

## 每个阶段具体采用什么方法

| 阶段 | 内置方法与适用条件 | 应交付的结果 |
| --- | --- | --- |
| 创意判断 | grilling 梳理决策依赖；grill-with-docs 与 domain-modeling 在需要沉淀业务语言时一起使用 | 用户问题、证据与反证、定位/MVP选项、验证实验 |
| 需求规格 | grilling + grill-with-docs + domain-modeling 推敲场景、术语、范围和业务边界 | 功能组合、主流程/异常流程、术语和明确选择、可验证 AC |
| 产品与视觉设计 | 先用场景和领域方法推敲产品流程，再用 frontend-design 比较视觉方向 | 信息结构、页面状态、线框或预览、已选视觉方案、组件规格 |
| 技术架构 | codebase-design 设计模块与接口；领域方法厘清业务边界，技术专项方法核对实现约束 | 技术选项与取舍、接口和数据契约、可行性证据 |
| 开发实现 | tdd、codebase-design 与技术栈专项方法；直接从 PRD 进入时补齐必要产品/设计推敲 | 代码、行为测试、运行证据及需求覆盖 |
| 测试修复 | 内置 test-case-design 先拆点、生成用例、补漏与评审，再由 webapp-testing 等执行；diagnosing-bugs 定位失败 | AC/TP/TC 用例集、逐例执行证据、缺陷与回归 |
| 部署验证 | 按已选平台核对官方配置；实际用容器时采用 docker-expert，失败时采用诊断方法 | 发布版本与地址、健康和关键路径、回滚记录 |

方法按条件启用，不会为了凑数量加载所有 Skill。已有明确产品和设计的简单修复，不会被迫再走一轮需求采访；没有 UI 的任务不强行生成视觉设计。

## 产品设计不是选颜色

例如你说“做一个预约工具”，Stagecraft 应先推敲谁在预约、服务资源是什么、如何处理冲突、取消和超时；再比较“用户直接选时段”和“提交申请后确认”等流程。

你选定产品流程后，才比较页面结构、信息优先级与视觉方向。技术方案根据这些已经明确的需求讨论，而不是先搭一个框架，再把产品塞进去。这是预期工作方式的说明，不是已完成案例或效果统计。

## 如何看出方法真正生效

每个阶段报告都记录方法、来源版本、为什么适用、实际做了什么，以及成果和证据路径。比如 grill-with-docs 应留下明确的业务术语与必要决策记录；frontend-design 应留下可比较方案与检查结果；测试方法应留下实际执行记录。

只写“遵循最佳实践”不算完成。阶段交接要传递具体成果：场景和术语进入需求，需求进入交互和设计，设计进入代码，测试与部署验证同一组已确认的行为。

## 筛选与适配原则

方法来源可追溯，保留原始版本和许可证；优先选择职责明确、可组合、能产生可检查成果的方法。内置源版本固定，避免上游更新在用户不知情时改变行为。不同宿主通过读取随包文件执行，不要求你再安装每一种底层 Skill。

本次引入的 grill-with-docs 来自 Matt Pocock 的固定源版本，组合 grilling 和 domain-modeling；后者使用 GLOSSARY.md。已有项目术语文档则沿用原路径，不因版本用词不同创建两份互相冲突的词表。

“精选实践”不代表已经证明在所有任务上优于其他方法。当前验证包括来源、依赖闭合、独立安装、协议和已有样本；新增方法组合仍需持续用真实产品任务评估。缺少平台专项方法、执行工具或真实证据时，报告必须说明限制。

各阶段成果不仅要生成，还要保存到项目并展示给用户评审。PRD、设计预览、技术方案、可运行版本、测试与发布材料均有版本和反馈记录；变更会追踪到下游验证。详见 [产物评审与全过程追溯](./artifact-reviews)。

## 详细覆盖与只读维护

七个阶段和测试用例子技能均提供详细指引，覆盖角色/数据/状态、设计、技术、验证、发布与运维等适用维度。普通产品执行保持第三方原文；维护者可通过更新、候选复核、备份和验证替换来源，适配和补充放在自研层。见 [Skills 覆盖范围与维护](./skill-coverage)。

## 最近采纳的方法升级

2026-10-21 维护中，前端设计、端到端测试和 SQL 优化三个方法切换到经过内容复核的 AAS 维护版本，阶段入口名称不变。设计强调明确的方向和约束，端到端测试强调可观察结果及失败证据，SQL 优化先验证正确性再比较性能。它们不是新增阶段，也不需要用户单独安装。

同轮拒绝了将通用 Vue/React 方法替换为某个 Markdown 渲染包集成指南等候选。职责适合比结构评分更重要；完整记录见[三方维护教程](./skill-maintenance#latest-review)。

## 关键方案确认与自动执行

## 先选方向，再自动执行

Stagecraft 不替你决定产品方向。每个阶段开始时先讨论本阶段方案；每个涉及选择的环节执行前，列出 2–3 个实际可行的选项，第一个始终是 agent 最推荐的方案，并解释推荐理由、适用条件与取舍。最后始终提示“如果都不合适，可以直接输入你的想法、约束或组合方案”。等待用户实际回复后再执行依赖该选择的工作；默认选中、沉默和等待超时都不算确认。已有明确选择直接复用，说明依据；用户明确委托的范围按委托执行。方案应解释实际差别，不要求你先懂技术术语。

| 关键节点 | 你会看到的方案 |
| --- | --- |
| 产品范围与功能模块 | 首期功能组合、可选项、暂不做的内容及取舍 |
| 产品设计 | 核心流程、页面结构、交互方式 |
| 视觉风格 | 有明显区别的方向，条件允许时提供线框、样例或预览 |
| 技术选型 | 技术栈和核心架构，比较成本、维护难度及部署限制 |
| 部署方式 | 本地或公网、平台、费用和访问范围 |

例如 agent 可以推荐“先做无需登录的单人版本”，同时说明“带账号同步版本”的能力、成本和开发范围。你可以回复“选 A”“按推荐方案继续”，也可以提出自己的方案。如果只有一种可行方案，agent 会说明原因，让你决定接受还是调整约束。

## 确认之后不反复打断

你明确提供的 PRD、对话和先前选择会被复用。已经选定技术栈或风格，就不会每个阶段重问。也可以明确说“视觉方案由你决定，其他关键选择先问我”；这只委托视觉范围，不会扩大为全部决定都由 agent 做。

“自动完成”“继续开发”不等于放弃关键选择。没有回复、默认高亮选项或 agent 自己写的草稿，都不算确认。等待选择时可以调研和制作标明用途的预览，但不会先把依赖该选择的产品做完再让你接受。

确认后，在选定方案内完成编码、验证和修复。完成当前环节后自动准备下一环节方案；每个阶段都讨论执行计划，测试阶段讨论覆盖与验收方案，部署阶段讨论上线与回滚方案。已明确确认过的计划说明依据后复用，不重复问相同问题。

## 决定如何保存和恢复

每个阶段报告记录决策 ID、备选方案、推荐理由、状态、你的选择或委托来源，以及影响范围。待选择时记录 blocked 和具体问题；回复后沿用同一工作流继续。换会话后也读取这些记录，不把未选择的建议当成已经批准。

## 什么时候算完成

每个阶段保存实际执行或检查证据；不把“计划运行”写成“已经通过”。失败时定位原因、修复并重新验证，默认最多三次有新证据的修复尝试；相同原因连续失败且无新信息时报告具体阻塞。

只要求分析或审计时，可以交付未选定的建议，但不能把建议直接当成下一阶段的实施许可。已授权修复可以自动执行；改变产品规则、降低验收标准或接受发布风险需要相应决定。

“只审计、不改业务代码”就只审计；“只设计界面”不会自动上线；“本机预览”不会自动创建云服务器。

## 你实际会看到的问法

> 本环节：首期产品范围。目标是尽快验证用户是否需要这个工具。
>
> 1. **单人使用、无需登录（最推荐）**：最快验证核心功能，成本低；暂不支持跨设备同步。
> 2. 账号与云端同步：多设备使用方便，但增加账号、数据存储和维护工作。
> 3. 先做可点击原型：更快收集反馈，但还不能处理真实业务。
>
> 如果都不合适，可以直接输入你的想法、约束或组合方案。

回复“选 1”即可，也可以说“我需要同步，但先不要注册账号”。agent 会吸收你的补充，检查可行性；如果含义或取舍还不明确，会给出调整后的方案与你确认，不擅自套回原选项。只剩一种可行方案时说明限制，不编造选项。

## 方案确认之后还要评审成果

同意方案只允许按方案工作，不等于验收未展示的成果。每个阶段都保存产物、展示实际内容，等你对具体版本评审；有意见就修订并展示差异，通过后才能交给下游。测试用例先评审再执行，发布清单先评审再上线，结果再交付评审。详见 [产物评审与全过程追溯](./artifact-reviews)。

## 产物评审与全过程追溯

Stagecraft 按需求评审、设计评审、技术评审、开发验收、测试评审和发布评审组织交付。你不仅选择方案，还要看到实际成果、提出修改意见、确认版本。小项目可以精简材料，大项目可以补充团队角色、检查项与评审流程；不会为了凑流程生成空文档。

## 每个阶段你会看到什么

| 阶段 | 项目中保存的成果 | 你评审什么 |
| --- | --- | --- |
| 产品探索 | 产品机会、目标用户、场景、MVP与验证计划 | 问题是否值得解决，首期方向是否合适 |
| 需求规格 | PRD、业务规则、流程、验收标准、非目标 | 做哪些功能、怎样使用、什么算完成 |
| 产品设计 | 设计源文件、实际预览/原型、交互与组件状态 | 页面效果、使用路径、空/错误/加载状态、不同屏幕 |
| 技术方案 | 架构图、接口与数据设计、取舍记录、开发任务 | 能力、成本、限制、风险及实施顺序 |
| 开发验收 | 代码、可运行版本、演示与启动方法、自测证据 | 是否符合已确认需求与设计，能否实际使用 |
| 测试评审 | 用例、覆盖映射、执行结果、缺陷与回归证据 | 测前看用例，测后看结果；哪些尚未验证 |
| 发布评审 | 发布清单、目标与版本、回滚方案；上线后地址及验证 | 发布前确认具体计划，发布后检查实际效果与交接 |

文档给可打开的路径，设计展示实际预览，应用展示运行效果。只有“PRD写好了”“设计完成了”的一句话不算展示。外部设计工具的源链接与版本也会记录；可导出的预览或说明保存到项目，无法完整导出时说明限制。

## 你如何评审和要求修改

agent 会说明本次成果版本、相对上版的变化、自检结果、已知问题和重点评审项，然后等待你的意见。

- “这版 PRD 通过，可以继续设计。”
- “不要手机号注册，先改成邮箱登录。”
- “设计稿的首页太复杂，把主要操作放到首屏。”
- “补上重复提交和断网恢复的用例，再给我看。”

回复普通文字即可，不需要写 JSON、操作状态机或记住命令。若意见有歧义，agent 会给出几个可行方案，推荐项在前并说明理由，最后允许你自由补充。方案有关键问题时，agent 应推荐修改，而不是默认引导你点“通过”。

同意前期方案不代表批准还没看到的成果；没有回复也不算通过。修改后会再次展示变化并提交新版本，旧版和旧意见保留。评审与下一阶段方案讨论可以合并呈现，但分别记录选择，减少无意义往返。

## 文件在哪里

优先沿用你的项目目录。没有既有约定时，推荐在 `docs/stagecraft/<工作流ID>/` 保存产物目录、PRD、设计说明、技术方案、测试和发布材料；源码仍在正常源码目录。

`.stagecraft/workflows/<工作流ID>/` 保存状态、阶段报告、每次提交的内容快照及用户评审记录。产物目录提供当前文件、版本、评审状态、上游依赖与证据链接，不需要你翻聊天记录寻找最新稿。

需求验收编号 AC 关联设计、技术决定和开发任务；测试点 TP 与测试用例 TC 关联同一需求；缺陷、修复和发布版本继续连接这些记录。这样可以追问“这个功能为什么这么做”“谁确认了这版规则”“哪条测试验证了它”。

## 中途修改会怎样

随时提出修改意见即可。agent 会记录变更原因、旧版/新版、影响的需求和下游成果，修改并重新验证。

例如 PRD 从“单人使用”改为“多人协作”，可能影响权限设计、界面、数据模型、代码和测试。旧版评审不能继续充当新版依据。相关阶段会标记为待重新检查，重新展示并评审；未变化的事实和已确认选择可以复用。

已经上线的版本不会因为修改文档自动回滚或重新发布。agent 先评估影响，按确认后的发布计划处理，记录真正部署的版本与结果。

## 可以直接复制给 agent

```text
使用 Stagecraft，按照 PRD.md 推进本项目。
每个阶段开始先讨论方案：推荐选项放第一，解释理由，最后允许我自由补充。
每个阶段的实际成果都保存到项目，维护一个可打开的产物目录。
PRD、设计稿、技术方案、开发效果、测试用例和结果、发布清单与上线结果，都要展示给我评审。
文档给文件链接，设计给实际预览，应用给运行演示和访问方式。
我提出修改后，修订、自检、展示差异并再次提交评审，不能自行当作通过。
具体版本经我确认后，再执行依赖该版本的下游工作；前期方案确认不等于成果验收。
测试先评审用例再执行，发布前先展示具体目标、版本、测试结论与回滚方案。
保留各次产物快照、我的意见、决定来源、需求到测试的映射和真实验证证据。
我随时可以修改前面阶段的成果；请说明下游影响，重新验证并评审相关版本。
不要让我手动维护状态文件，不把未经评审或未经验证的阶段说成完成。
```

## 旧工作流如何继续

新版交接助手采用 v2，增加“提交评审、记录意见、批准后完成”步骤。打开旧 v1 工作流时会备份旧状态，保留原文件与证据，将已有工作标记为需要重新检查和评审；不会伪造之前已经评审过。

工具能检查文件是否改变、版本是否对应、记录是否齐全，不能独立证明用户身份或实际评审是否发生。agent 必须记录真实回复，不能自行编造批准。没有 Node.js 时使用等价文件和评审记录，明确自动校验能力的限制。

## 测试用例与执行

测试不是直接运行几个命令再告诉你“通过了”。Stagecraft 先把产品需求变成能检查的用例，再执行这些用例，告诉你哪些通过、哪些失败、哪些还没有条件验证。

## 不需要额外选装

新版 `stagecraft-test` 内置 `stagecraft-test-case-design`。调用测试阶段时会先使用它，不用自己挑选底层技能。当前 npm 0.4.1 已发布；以下演示 GitHub 安装，固定版本的 npm 方式见[技能安装](./packages)：

```sh
npx skills add Jahseh-bot/stagecraft --skill stagecraft-test
```

已有安装运行 `npx skills update`，然后让 agent 重新加载技能。没有自动发现时，让它读取安装目录中的 `stagecraft-test/SKILL.md`；只设计用例也可以让它读取该目录下 `references/test-case-design/SKILL.md`。

## 实际会怎样进行

1. **讨论方案**：读取 PRD 和已有决定，提出符合任务规模的测试覆盖方案。第一个是最推荐的方案并解释理由，其他选项说明成本与覆盖差异；你始终可以直接输入自己的要求。
2. **拆测试点**：整理正常流程、输入边界、异常恢复、业务规则以及适用的非功能风险，连接对应需求。
3. **生成具体用例**：每条都有前置条件、数据、操作步骤和可观察预期。默认输出 Markdown 文档；已有团队模板优先，Excel/XMind 按你的需要和工具能力提供。
4. **补漏与评审**：结合实际风险和可获得的历史缺陷补充场景，修正含糊预期、不可执行步骤与重复用例。核心规则不清楚时与你讨论，不自行猜测。
5. **按例测试**：展示用例集并获得具体版本的评审确认后，将用例对应到脚本或浏览器操作，逐条保存实际结果与证据。只生成文档不算执行完成。
6. **修复与回归**：在授权范围内修复失败项，重测原失败用例和受影响场景，保留前后记录。新增业务取舍或范围变化仍先与你讨论。

已确认的方案直接复用，不会要求你逐条批准每一条用例。每个尚未确定的方案与业务规则都允许讨论和自定义补充。

## 可以直接复制给 agent

```text
使用 stagecraft-test 测试当前项目，以 PRD.md 和已确认的需求为依据。
先使用内置 stagecraft-test-case-design，完成测试点拆解、用例生成、风险补漏和质量评审，然后再执行测试。
每个环节需要选择时先给可行方案，第一个是你最推荐的并解释理由，最后允许我自由补充。
先讨论覆盖范围；业务规则、边界或预期不明确时与我讨论，不要自行补成需求。
已有明确确认的方案直接复用，不要逐条重复询问。
用例应包含具体数据、步骤、预期、优先级和需求编号；请让我看到核心用例、覆盖缺口与待决问题。
将用例集保存到项目并展示给我评审；确认具体版本后按用例测试，逐条记录实际结果、环境、版本与证据。
测试报告也要展示评审，修改时保留版本和反馈，确认后再交给部署。
在本次需求范围内修复发现的问题，再重测失败用例与受影响回归。
不要把用例已生成、评审可用或整套命令退出成功当成所有用例通过。
最后交付用例文档、覆盖映射、执行结果、缺陷和回归证据，说明哪些没有验证及原因。
```

只想先审阅用例，可以把修复那句话改为：“本次只生成和评审用例，不执行测试，不修改业务代码。”

## 怎样读结果

`AC` 是需求验收编号，`TP` 是测试点，`TC` 是具体用例。通过这些编号，可以从产品需求一直找到实际测试证据。

用例评审状态为可用、待修改或排除；执行状态另行记录为通过、失败、阻塞、未执行或跳过。缺少账号或工具属于阻塞，不能填“通过”。报告分别列出设计覆盖和执行覆盖，并说明统计分母；有关键缺口时不会给出无条件可上线结论。

例如温度换算不仅检查“输入 0 得到 32”，还检查“有结果后清空输入，旧结果消失并显示指定提示”。如果需求没说是否允许低于绝对零度，会先讨论产品规则，再确定相关预期。

## 查看成果与启动网页

## 找到交付结果

agent 在每个阶段都应展示实际成果并提交用户评审，不等到最后才交付。项目中的产物目录列出最新文件、版本、预览、评审状态及证据；最终还应给出启动方法和仍未验证的部分。交接报告通常在目标项目 `.stagecraft/workflows/任务编号/` 下，文件可直接在编辑器里打开。

检查报告里的 AC（验收编号），确认你的每个要求都有对应成果及证据。“completed”表示本次约定范围的产物和必要验证完成、具体版本已获用户评审通过，不是保证软件没有任何缺陷。

## 打开网页

按 agent 给出的具体启动命令操作。不同项目的命令和端口不同，不要照抄其他项目的地址。例如项目确实提供 `dev` 脚本时：

```sh
npm run dev
```

终端显示本地地址后，用浏览器打开它。逐一试试温度换算、空值、非法输入和清空按钮。测试时临时启动的服务可能已经关闭；交付说明应明确是否需要你重新启动。

不要双击源码 HTML 代替项目启动流程。若启动失败，把错误直接发给当前 agent，让它根据交接记录继续诊断。

## 部署与发布验证

已有 PRD、希望一次完成开发到部署？直接使用[从 PRD 自动衔接的完整提示词](./first-run#prd-to-deploy)，其中包含技能准备、部署目标示例和中断恢复方法。

## 向 agent 说明目标

安装 deploy 技能后，明确目标、权限和你希望公开的内容。不知道如何选择时，要求 agent 给出部署方案、费用、限制和推荐理由，等你确认后再发布。例如：

```text
使用 stagecraft-deploy，把这个静态网站部署到我已授权的 GitHub Pages 仓库。
配置后续更新自动发布，等待流水线完成，验证公网地址和关键页面，再给我链接。
```

也可以指定已有服务器、本机服务或其他平台。Skill 按当前 agent 的工具和目标配置执行，不强制 Docker，也不会自动购买资源。

## 不知道部署到哪里

| 目标 | 适合什么情况 | 需要说明 |
| --- | --- | --- |
| 电脑本机预览 | 自己检查页面和交互 | 不是公网，终端关闭后服务可能停止 |
| GitHub Pages | 构建后是静态文件的网站 | 仓库、Pages 配置和授权；不能承载独立后端服务 |
| 已有托管平台项目 | 平台支持的前后端应用 | 实际账号、项目、构建配置、费用与环境变量 |
| 自有服务器 | 需要自行运行后端或服务 | SSH 配置、允许修改的目录/服务、备份与回滚 |
| 本机 Docker | 希望本机可重复运行服务 | 已启动的 Docker、端口和数据存储位置 |

先由 agent 根据真实项目推荐，选项 1 说明理由，最后允许自由补充。不要为了发布一个静态页被迫创建数据库；也不要把本机地址当作手机或他人可直接打开的地址。

## 发布前你要评审什么

看具体版本、测试结果、目标账号与仓库、公开范围、配置、数据迁移、费用及回滚步骤。确认的是这份发布清单。agent 不能拿先前“选这个平台”的回复代替对尚未展示清单的评审。

上线后打开实际地址，验证核心路径；agent 记录部署的提交或制品版本。遇到验证失败，应说明是未发布、发布失败还是结果未知，按已确认计划修复或回滚。

## 完整发布闭环

部署前检查实际版本、测试结果、构建和配置；部署后核对实际运行的修订版本、地址、健康与关键路径。推送成功或旧实例仍健康都不代表本次上线成功。

失败时诊断并在授权范围内修复，必要时按已授权计划回滚并验证。凭据、账单、DNS等必须由你处理的阻塞，会留下具体状态和恢复步骤。不能访问生产环境时不会伪造已发布结论。

旧 runner 的 deploy 命令仍只支持本机 Docker Compose；本页描述的是在当前 agent 中执行的新版 deploy Skill。

## 恢复与处理失败

## 在同一或另一个 agent 中继续

在新会话打开同一项目，然后说：

```text
读取 .stagecraft/workflows 中与温度换算项目对应的交接记录，继续未完成阶段。
保留已确认需求与我的改动；先检查已有成果和验证是否仍有效，不要重新采访或从头再做。
```

如果有多个同类任务，提供具体工作流目录。agent 无法确定哪个记录对应你的目标时，应只问这个选择问题。

## 上游改动会使旧结果失效

助手记录关键成果和日志的 SHA-256。文件改动或丢失时，相关阶段与后续记录会标为 stale。测试修复了业务代码后，要重新验证并记录构建结果，重新展示并评审修改后的成果，再完成受影响测试，不能沿用修改前的通过结论。

## 外部阻塞

网络、凭据、目标服务或权限不可用时，agent 应保存已完成动作、具体原因及下一步。必要验证未执行就标为 blocked/partial，不应一直无意义重试。

## 旧 runner 任务

`.stagecraft/runs` 是旧运行器记录，新技能使用 `.stagecraft/workflows`，两者不能混写。旧记录仍可用创建它的 runner 版本恢复。迁移到 Skill 时读取旧记录中的需求和已确认决定作为输入，不自动把旧状态转换为新版已完成记录。

## 恢复评审或修改意见

未评审的成果保持待评审状态，不因换会话就算通过。agent 会读取产物快照、对应评审和你的修改意见，展示当前版本及差异，沿用已确认且未变化的决定。旧 v1 工作流先备份再重新检查/评审；详见 [产物评审与全过程追溯](./artifact-reviews)。

## 已有项目测试与修复

## 直接从测试切入

不需要先跑创意、需求、设计和开发阶段。安装 test 技能后，在已有项目中说：

```text
使用 stagecraft-test，检查本次改动，补充必要测试并修复范围内的问题，运行回归。
保留现有测试，不要通过删断言获得通过。记录基线、失败原因、修复和最终证据。
```

只希望得到报告时改成：

```text
使用 stagecraft-test，只审计这个项目，不修改业务代码。
实际运行可用检查，交付缺陷复现步骤、证据和修复建议。
```

“审计完成”可以包含发现的失败，不能写成“产品测试通过”。纯 URL 测试应说明源码检查、内部权限路径等覆盖限制。

## 已有代码，也要方案和评审

让 agent 先读取当前框架、约定、未提交改动和已有测试，提出本轮范围与验收方案。测试用例集先展示评审，再执行；结果与修复也要展示。保留无关改动，遇到产品规则或架构变化重新给选项。

```text
使用 Stagecraft 继续这个已有项目，先检查仓库和已有工作流。
本轮目标：修复我刚才描述的问题，不重搭框架、不扩大功能。
先列出推荐修复与验证方案，等我确认；保留无关改动。
复用有效需求，补足并评审必要用例，然后实现、测试与回归。
展示代码变化、运行结果和证据，保存记录供我评审；本次不部署。
```

## 版本与迁移

## 普通用户：更新已安装的 Skills

本教程使用 GitHub 当前版本。先保存产品项目的代码和需求，备份自己改过的技能文件，再在当初安装 Skills 的项目目录运行：

```sh
npx skills check
npx skills update
```

`update` 会检查并更新安装工具登记的 Skills，可能包含你安装的其他来源，阅读输出后确认本次实际更新了什么。更新后重新加载宿主技能或新开项目会话，请 agent 列出读取的 Stagecraft 入口与路径。

这更新的是方法文件，不会自动修改产品代码、批准新成果或重新部署。继续已有任务时，要求 agent 读取原工作流，检查新版方法对当前任务和证据的影响。

## 以前通过 npm 阶段包安装

npm 安装器复制的文件不一定登记在通用 skills CLI 的来源记录中。如果 `npx skills update` 没有识别到 Stagecraft：

1. 记下旧 Skill 目录，备份自己的改动。
2. 把旧的七个 Stagecraft 技能目录移出宿主扫描位置，保留备份；不要删除产品源码或 `.stagecraft`。
3. 在产品项目目录运行 `npx skills add Jahseh-bot/stagecraft`，选择需要的阶段和宿主。
4. 重新加载后核对实际读取路径，避免同时加载项目版与全局旧版。

安装冲突时先比较文件，不盲目强制覆盖。

## 当前版本状态与固定来源

2026-10-21，全部八个 npm 包已发布 0.4.1。0.4.0 不包含本次完整评审与方法升级；请使用 0.4.1 或当前 GitHub Skills。查看注册表版本：

```sh
npm view @gaaraa/build version --registry=https://registry.npmjs.org
```

团队需要完全复现时，记录所安装的 Stagecraft 提交、来源与安装输出，并使用经团队核验的固定提交副本；不要把持续变化的 main 当成固定版本。固定本次版本可用[七阶段 npm 0.4.1 安装命令](./packages)。npm 安装器不会覆盖不同内容：升级前备份旧技能，将旧目录移出宿主扫描位置后重装；不要删除产品源码和工作流。以后版本以[更新记录](/changelog/)的实际状态为准。

## 维护者：更新 Stagecraft 内置三方方法

`npm run update-skills` 和 `npm run upgrade-skills` 是 **Stagecraft 源码仓库**的维护命令，不是在你的产品项目里运行的通用更新命令。

前者追踪已登记来源，后者搜索替代候选。候选可能评分更高却不适合原职责，仍需要内容复核。详见[三方 Skills 维护](./skill-maintenance)。

## 从旧 runner 任务迁移

旧 `.stagecraft/runs` 保留原样，用创建该任务的版本恢复，或把其中的需求、决定和报告作为新 Skills 输入。新工作流位于 `.stagecraft/workflows`，不能把旧状态文件直接复制进去当作已验收成果。

0.3.0 是旧 runner；0.3.1 曾部分发布，不作为当前完整安装路线。旧命令集中在 [CLI 兼容参考](/cli/#legacy-runner)。

## Windows、macOS 和 Linux

技能主体是通用 Markdown。安装器和助手使用 Node.js 路径 API；终端命令中的项目路径要换成你的系统路径。自动化和真实小任务验证的执行主机是 macOS，不能据此宣称所有操作系统、宿主和工具链都实机验证。

宿主权限和信任提示由宿主控制。Stagecraft 不绕过这些提示，也不提供模型账号、云服务器或数据库凭据。

## Skills 覆盖范围与维护

Stagecraft 为每个阶段提供入口 Skill、详细工作指引、跨阶段覆盖表、评审规则与方法适配说明。agent 根据任务读取和应用，不需要你逐个选择底层技能。

## 各阶段新增的详细内容

| 阶段 | 重点覆盖 |

## 全面检查，但不强塞功能

开始阶段时，agent 会判断相关维度为“适用”“不适用”或“未知”，并给出依据。比如没有账号的本地工具无需虚构多租户方案；需要多人协作的系统则不能漏掉资源权限、并发和状态恢复。

同时考虑新项目、存量系统、单点修复，以及 Web、移动、桌面、CLI、API、数据任务和 AI 产品。材料深度随任务和风险调整；通用流程不能代替特定行业的专业审查，也不代表所有技术环境已经验证。

你的控制权保持不变：关键方案推荐项在前，允许自由补充；每阶段成果保存并展示，具体版本评审通过后再交接。新增覆盖项若会扩大功能、成本或风险，先讨论再实施。

## 第三方 Skills 保持原样

正常产品开发中，现有三方方法的文件、示例和许可证不修改、不删除。用户显式运行维护命令时，可以核验上游后更新或替换，保存备份、来源和报告；见 [自动更新与升级 Skills](./skill-maintenance)。宿主工具差异、范围限制和缺失能力放在 Stagecraft 自研的 `references/upstream-adapters.md` 中说明。

新增三方方法需要来源、固定版本、许可证、引用依赖、适用范围和产物验证，不为了凑数量增加。当前仍保留 40 个独立三方方法；按阶段打包的副本不算新增方法。

一项已知限制是 `python-design-patterns` 的延伸链接指向尚未捆绑的 `python-project-structure`。原文保持不变，agent 会明确该方法不可直接调用，使用自研架构指引和既有仓库约定完成可验证的工作；需要专项能力时再研究并新增，不能假装已经执行。

## 可重复扫描

项目维护者在仓库运行：

```sh
npm run build
npm run audit:skills
```

报告保存到 `output/audits/skills.json`，包括入口元数据、文件引用、来源版本与三方源内容哈希。它检查结构、完整性与只读约束；不能证明每个 Skill 在所有宿主、产品或技术栈上的实际效果。真实任务的产物评审与验证证据仍然不可省略。

## 自动更新与升级 Skills

这两个命令由 **Stagecraft 仓库维护者**在仓库根目录执行，用于维护随产品发布的三方方法。普通使用者更新已安装的 Stagecraft 仍用 `npx skills update`。

## 两个命令的区别

| 命令 | 做什么 | 不会做什么 |
| --- | --- | --- |
| `npm run update-skills` | 检查全部已登记三方 Skill 的原仓库，获取默认分支最新提交，核验后更新源文件、版本记录和分发副本 | 不换成另一个作者的不同方法 |
| `npm run upgrade-skills` | 实际搜索公开 GitHub 技能仓库，按职责匹配和明确规则比较候选，自动替换合格且评分明显改善的方法 | 不因星标多就替换，不保证找到“全市场最好”的方法 |

两者默认应用合格变更，然后执行项目测试（含构建）和 Skills 审计。验证失败自动恢复维护前的源与生成文件；有被阻塞的条目会报告并以非零状态退出，不把部分成功说成全部完成。没有合格替代者时保留原项。

“最新”明确指上游仓库**默认分支的最新提交**，不等同最新稳定发行版。来源锁定到具体提交 SHA，后续普通构建不会自行追踪线上变化。

## 开始前

1. 在终端进入 Stagecraft 仓库根目录，确认能看到本项目 `package.json`。
2. 使用项目要求的 Node.js 和 npm，并确保能访问 GitHub API 与 raw.githubusercontent.com。
3. 正式应用前先提交当前工作，或用 `git stash push -u` 收起未提交的改动，确保工作区干净（仅 `git add` 暂存还不够）。命令不自动提交、推送或发布 npm；如果上一轮已产生改动，先审阅和提交后再开始下一轮。
4. 大范围搜索建议配置 `GITHUB_TOKEN` 环境变量，以使用对应的 GitHub API 配额。公开仓库读取无需扩大到私有仓库权限；不要把令牌写进代码或报告。

先只看报告也可以：

```sh
npm run update-skills -- --dry-run
npm run upgrade-skills -- --dry-run
```

预检会联网读取并生成报告，不替换现有技能；允许在工作区已有改动时运行。

## 正式更新

```sh
npm run update-skills
```

命令会尝试所有现有三方方法。仓库改名时只跟随有上限的 GitHub 同源重定向，并记录规范仓库名。原目录移动时只接受可唯一定位的同名目录；身份变化、来源不可用、新增缺失引用、无法确认许可证等情况保留旧方法并报告原因。最新提交与本地版本相同但文件或许可证打包有差异时，报告为同版本内容同步，不冒称发现新版本。

只维护指定方法：

```sh
npm run update-skills -- --only grilling,frontend-design
```

## 自动搜索替代方法

```sh
npm run upgrade-skills
```

默认按配置中的产品/测试/设计/架构等关键词搜索公开 GitHub 仓库，结合既有来源，在有界的仓库和候选数量内筛选。配置位于 `tooling/skill-maintenance.config.json`，可调整查询、仓库数、每个技能的候选数、最低提升分差、允许许可证及角色关键词。

```sh
npm run upgrade-skills -- --dry-run --only frontend-design --max-repos 20
```

候选必须通过：

- 入口声明的用途与正文都要匹配职责和技术领域；排除已安装的互补专项方法。
- 有可识别且允许分发的许可证文本，Skill 声明不与之冲突。
- 文件与大小限制、入口元数据、必要本地引用完整性检查。
- 跳过 `rejectedCandidates` 中已复核不适用的精确来源版本，报告拒绝原因。
- 文档结构评分达到配置的最低提升幅度，再通过 Stagecraft 构建与测试。

评分目前观察适用说明、执行流程、验证、恢复、示例、产物、约束和引用等内容，报告保留各项依据。**这是自动筛选的启发式，不能证明候选在真实任务中更优秀**；热点、更新时间和用例数量也不是效果证明。命令不执行下载方法自带的脚本来给它自己打分。源文件保留原文，以稳定的 Stagecraft 方法 ID 连接现有阶段，不重命名用户的阶段入口。

## 查看报告与恢复

每次运行打印记录ID，成果位于：

```text
output/skill-maintenance/<记录ID>/
  report.json        # 搜索范围、候选评分、变化和阻塞
  report.md          # 人可读摘要（正常完成后）
  transaction.json  # 应用/回滚状态（实际应用时）
  backup/           # 原始源、版本锁及生成文件
  tests.log         # 实际项目测试输出
  audit.log         # 应用后的审计输出
```

不要在确认更新结果前删除备份。恢复某次成功更新：

```sh
npm run update-skills -- --restore 这里替换为记录ID
```

恢复前会核对备份和更新后的文件状态；如果你又编辑了相关文件，会拒绝覆盖。先保存后续工作；确实要用备份覆盖维护范围时，才加 `--force-restore`。

进程异常中断时，先检查根目录 `.stagecraft-skills-maintenance.lock` 记录的进程是否仍在运行，不要同时启动两个维护程序。确认原进程已结束后移除遗留锁，检查 `transaction.json` 和备份，再用 `--restore <记录ID> --force-restore` 恢复中断事务；未完成备份的记录不能当作可恢复事务。

## 三方只读规则的例外

正常产品开发和手工补充仍不改写、删除三方原文。用户显式运行这两个维护命令时，允许从已核验上游更新或由候选替换，配套更新来源锁和完整性基线，保留备份和变更报告。自研阶段协议、用户评审机制和适配说明不会被搜索结果替换。

GitHub 的搜索范围和配额有边界；遇到限流或网络问题，报告会保留具体条目，配置有效令牌或等待配额恢复后重试。不会在搜索失败时编造“没有更好的技能”。参见 [GitHub 搜索接口说明](https://docs.github.com/en/rest/search/search) 与 [仓库接口说明](https://docs.github.com/en/rest/repos/repos)。


## 评分之后还需要内容复核

默认命令会应用通过机器筛选的候选，不会自动等待人工评审。正式维护前可以先 `--dry-run` 查看计划；正式应用后、提交推送前，仍要对照原方法检查职责、示例、引用资源、许可证和专业覆盖。测试通过不能证明新方法更适合产品。

如果发现候选范围变窄、丢失关键内容或引用不存在的示例，先用备份恢复本轮，再将精确版本与原因记录到 `tooling/skill-maintenance.config.json` 的 `rejectedCandidates`。它不是永久封禁作者；上游换版本后需要重新评估。不要只为获得升级数量而替换。

顺序运行两个命令时，第一轮可能产生文件改动。先评审结果并提交（或恢复），让工作区干净，再运行下一轮。不要把未经复核的自动变更直接发布。
