# 部署与发布验证

已有 PRD、希望一次完成开发到部署？直接使用[从 PRD 自动衔接的完整提示词](./first-run#prd-to-deploy)，其中包含技能准备、部署目标示例和中断恢复方法。

## 向 agent 说明目标

安装 deploy 技能后，明确目标、权限和你希望公开的内容。不知道如何选择时，要求 agent 给出部署方案、费用、限制和推荐理由，等你确认后再发布。例如：

```text
使用 stagecraft-deploy，把这个静态网站部署到我已授权的 GitHub Pages 仓库。
配置后续更新自动发布，等待流水线完成，验证公网地址和关键页面，再给我链接。
```

也可以指定已有服务器、本机服务或其他平台。Skill 按当前 agent 的工具和目标配置执行，不强制 Docker，也不会自动购买资源。

## 不知道部署到哪里

| 目标 | 适合什么情况 | 需要说明 |
| --- | --- | --- |
| 电脑本机预览 | 自己检查页面和交互 | 不是公网，终端关闭后服务可能停止 |
| GitHub Pages | 构建后是静态文件的网站 | 仓库、Pages 配置和授权；不能承载独立后端服务 |
| 已有托管平台项目 | 平台支持的前后端应用 | 实际账号、项目、构建配置、费用与环境变量 |
| 自有服务器 | 需要自行运行后端或服务 | SSH 配置、允许修改的目录/服务、备份与回滚 |
| 本机 Docker | 希望本机可重复运行服务 | 已启动的 Docker、端口和数据存储位置 |

先由 agent 根据真实项目推荐，选项 1 说明理由，最后允许自由补充。不要为了发布一个静态页被迫创建数据库；也不要把本机地址当作手机或他人可直接打开的地址。

## 发布前你要评审什么

看具体版本、测试结果、目标账号与仓库、公开范围、配置、数据迁移、费用及回滚步骤。确认的是这份发布清单。agent 不能拿先前“选这个平台”的回复代替对尚未展示清单的评审。

上线后打开实际地址，验证核心路径；agent 记录部署的提交或制品版本。遇到验证失败，应说明是未发布、发布失败还是结果未知，按已确认计划修复或回滚。

## 完整发布闭环

部署前检查实际版本、测试结果、构建和配置；部署后核对实际运行的修订版本、地址、健康与关键路径。推送成功或旧实例仍健康都不代表本次上线成功。

失败时诊断并在授权范围内修复，必要时按已授权计划回滚并验证。凭据、账单、DNS等必须由你处理的阻塞，会留下具体状态和恢复步骤。不能访问生产环境时不会伪造已发布结论。

旧 runner 的 deploy 命令仍只支持本机 Docker Compose；本页描述的是在当前 agent 中执行的新版 deploy Skill。
