# 创建需求说明

## 用普通话描述你要的结果

你可以在 agent 会话里直接描述，不强制先写 PRD。需求复杂时，在目标项目新建 `PRD.md` 文本文件，写清楚给谁使用、主要功能、范围和完成标准。

例如：

```md
# 温度换算网页

给普通人使用，中文界面，适配电脑与手机尺寸。
输入摄氏度或华氏度，显示另一种温度，保留一位小数。
支持清空；空值和非法数字显示中文提示。
只在本机运行，不需要账号、数据库、支付或外部 API。
验收：0℃ = 32.0℉；100℃ = 212.0℉；32℉ = 0.0℃。
请实际运行测试，给出本地启动命令和浏览器地址。
```

第一次不要把真实密码、Token、私密业务数据写进需求。需要外部服务时使用宿主已有的凭据机制；敏感值不写进交接报告。

如果需求仍不清楚，可以先安装 `spec` 技能，让 agent 从现有材料补足可验收规则。它只会集中询问真正影响业务含义的缺口。

## 只有想法，没有 PRD

在安装七阶段 Skills 后，把下面内容发给 agent：

```text
使用 stagecraft-discover 和 stagecraft-spec，帮我把这个想法整理成可评审的 PRD。
我的想法：做一个中文温度换算工具。
先讨论用户、场景、首期功能和边界。每次给可行方案，推荐项放第一并说明理由，允许我自由补充。
沿用已有资料，不替我决定尚未确认的产品规则。
把 PRD、验收标准、决定和待决问题保存到项目，展示实际文件让我评审。
这次先停在 PRD 评审，不开始写产品代码。
```

PRD 评审通过后，使用[完整交付提示词](./first-run#prd-to-deploy)继续。只有范围确实适用时才进入设计与架构；已有资料不重复生成。
