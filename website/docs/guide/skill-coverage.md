# Skills 覆盖范围与维护

Stagecraft 为每个阶段提供入口 Skill、详细工作指引、跨阶段覆盖表、评审规则与方法适配说明。agent 根据任务读取和应用，不需要你逐个选择底层技能。

## 各阶段新增的详细内容

| 阶段 | 重点覆盖 |
| --- | --- |
| 产品探索 | 用户与购买者、场景、证据与反证、替代方式、价值/成本、分发假设、MVP与验证实验 |
| PRD | 范围、角色权限、主/分支/异常流程、状态规则、数据字典、质量约束、AC验收与变更 |
| 产品设计 | 信息结构、线框与流程、视觉选项、完整页面状态、响应式、可访问性、资源与实现交接 |
| 技术架构 | 系统/模块/数据/API边界、并发与一致性、依赖失败、安全/性能/成本、技术探针、迁移与任务拆分 |
| 开发 | 垂直切片、真实集成、错误与恢复、数据迁移、多端/API/CLI/后台/AI、自测和代码差异检查 |
| 测试 | 用例设计评审、分层验证、环境数据、权限/兼容/性能/恢复、AI评估、缺陷诊断与回归 |
| 部署 | 可复现制品、环境配置、迁移、发布策略、发布前后评审、版本核实、回滚和运维交接 |

每个阶段的安装目录内都有 `references/stage-guide.md`，可直接查看详细执行步骤；`references/coverage.md` 提供跨阶段的适用性矩阵。

## 全面检查，但不强塞功能

开始阶段时，agent 会判断相关维度为“适用”“不适用”或“未知”，并给出依据。比如没有账号的本地工具无需虚构多租户方案；需要多人协作的系统则不能漏掉资源权限、并发和状态恢复。

同时考虑新项目、存量系统、单点修复，以及 Web、移动、桌面、CLI、API、数据任务和 AI 产品。材料深度随任务和风险调整；通用流程不能代替特定行业的专业审查，也不代表所有技术环境已经验证。

你的控制权保持不变：关键方案推荐项在前，允许自由补充；每阶段成果保存并展示，具体版本评审通过后再交接。新增覆盖项若会扩大功能、成本或风险，先讨论再实施。

## 第三方 Skills 保持原样

正常产品开发中，现有三方方法的文件、示例和许可证不修改、不删除。用户显式运行维护命令时，可以核验上游后更新或替换，保存备份、来源和报告；见 [自动更新与升级 Skills](./skill-maintenance)。宿主工具差异、范围限制和缺失能力放在 Stagecraft 自研的 `references/upstream-adapters.md` 中说明。

新增三方方法需要来源、固定版本、许可证、引用依赖、适用范围和产物验证，不为了凑数量增加。当前仍保留 40 个独立三方方法；按阶段打包的副本不算新增方法。

一项已知限制是 `python-design-patterns` 的延伸链接指向尚未捆绑的 `python-project-structure`。原文保持不变，agent 会明确该方法不可直接调用，使用自研架构指引和既有仓库约定完成可验证的工作；需要专项能力时再研究并新增，不能假装已经执行。

## 可重复扫描

项目维护者在仓库运行：

```sh
npm run build
npm run audit:skills
```

报告保存到 `output/audits/skills.json`，包括入口元数据、文件引用、来源版本与三方源内容哈希。它检查结构、完整性与只读约束；不能证明每个 Skill 在所有宿主、产品或技术栈上的实际效果。真实任务的产物评审与验证证据仍然不可省略。
