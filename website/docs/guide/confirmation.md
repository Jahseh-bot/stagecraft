# 关键方案确认与自动执行

## 先选方向，再自动执行

Stagecraft 不替你决定产品方向。每个阶段开始时先讨论本阶段方案；每个涉及选择的环节执行前，列出 2–3 个实际可行的选项，第一个始终是 agent 最推荐的方案，并解释推荐理由、适用条件与取舍。最后始终提示“如果都不合适，可以直接输入你的想法、约束或组合方案”。等待用户实际回复后再执行依赖该选择的工作；默认选中、沉默和等待超时都不算确认。已有明确选择直接复用，说明依据；用户明确委托的范围按委托执行。方案应解释实际差别，不要求你先懂技术术语。

| 关键节点 | 你会看到的方案 |
| --- | --- |
| 产品范围与功能模块 | 首期功能组合、可选项、暂不做的内容及取舍 |
| 产品设计 | 核心流程、页面结构、交互方式 |
| 视觉风格 | 有明显区别的方向，条件允许时提供线框、样例或预览 |
| 技术选型 | 技术栈和核心架构，比较成本、维护难度及部署限制 |
| 部署方式 | 本地或公网、平台、费用和访问范围 |

例如 agent 可以推荐“先做无需登录的单人版本”，同时说明“带账号同步版本”的能力、成本和开发范围。你可以回复“选 A”“按推荐方案继续”，也可以提出自己的方案。如果只有一种可行方案，agent 会说明原因，让你决定接受还是调整约束。

## 确认之后不反复打断

你明确提供的 PRD、对话和先前选择会被复用。已经选定技术栈或风格，就不会每个阶段重问。也可以明确说“视觉方案由你决定，其他关键选择先问我”；这只委托视觉范围，不会扩大为全部决定都由 agent 做。

“自动完成”“继续开发”不等于放弃关键选择。没有回复、默认高亮选项或 agent 自己写的草稿，都不算确认。等待选择时可以调研和制作标明用途的预览，但不会先把依赖该选择的产品做完再让你接受。

确认后，在选定方案内完成编码、验证和修复。完成当前环节后自动准备下一环节方案；每个阶段都讨论执行计划，测试阶段讨论覆盖与验收方案，部署阶段讨论上线与回滚方案。已明确确认过的计划说明依据后复用，不重复问相同问题。

## 决定如何保存和恢复

每个阶段报告记录决策 ID、备选方案、推荐理由、状态、你的选择或委托来源，以及影响范围。待选择时记录 blocked 和具体问题；回复后沿用同一工作流继续。换会话后也读取这些记录，不把未选择的建议当成已经批准。

## 什么时候算完成

每个阶段保存实际执行或检查证据；不把“计划运行”写成“已经通过”。失败时定位原因、修复并重新验证，默认最多三次有新证据的修复尝试；相同原因连续失败且无新信息时报告具体阻塞。

只要求分析或审计时，可以交付未选定的建议，但不能把建议直接当成下一阶段的实施许可。已授权修复可以自动执行；改变产品规则、降低验收标准或接受发布风险需要相应决定。

“只审计、不改业务代码”就只审计；“只设计界面”不会自动上线；“本机预览”不会自动创建云服务器。

## 你实际会看到的问法

> 本环节：首期产品范围。目标是尽快验证用户是否需要这个工具。
>
> 1. **单人使用、无需登录（最推荐）**：最快验证核心功能，成本低；暂不支持跨设备同步。
> 2. 账号与云端同步：多设备使用方便，但增加账号、数据存储和维护工作。
> 3. 先做可点击原型：更快收集反馈，但还不能处理真实业务。
>
> 如果都不合适，可以直接输入你的想法、约束或组合方案。

回复“选 1”即可，也可以说“我需要同步，但先不要注册账号”。agent 会吸收你的补充，检查可行性；如果含义或取舍还不明确，会给出调整后的方案与你确认，不擅自套回原选项。只剩一种可行方案时说明限制，不编造选项。
